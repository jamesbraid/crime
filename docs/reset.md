# Rendering engine initialisation and error recovery, and the kernel's use of the memory transfer engine

What the IRIX 6.5.30 kernel writes to bring the rendering engine to a known state, how it recovers after an engine error, and how its own bulk-memory helpers drive the memory transfer engine (MTE). Register names are in [CRIME_RE.h](../CRIME_RE.h) and [MTE.h](../MTE.h). Labels: **established** (read from the cited function in the decompilation under `crime_kernel/decomp/` and checked against the object disassembly), **inferred**, **unknown**. `k:` is the kernel (`crime_init.o`, `crime.o`, `kernel.o`).

## Initialisation (`k:crime_init:crimeInitHW`)

Order of the writes (established):
1. Write `+0x408` with 0. Write GBE `+0x70004` (cursor control, `GBE_CRS_CTL`; bit 0 enables) with 0.
2. Write the interface-buffer control register (`IB_CTL`, `+0x400`) with the boot value `0x0fefff0a` (fields in `CRIME_RE.h`).
3. Clear the three frame-buffer TLBs (`+0x1000`, `+0x1200`, `+0x1400`, 64 doublewords each), pausing after every eighth entry to wait for the interface buffer to drain (`crmFifoWait`, 4096 polls) and writing 0 to `+0x4008`.
4. Clear linear TLBs A and B (`+0x1700`, `+0x1780`, 16 doublewords each), wait for the buffer to drain and write `+0x4008` with 0.
5. Clear the texture TLB (`+0x1600`, 28 doublewords) and write `+0x4008` with 0.
6. If the caller asks for it, program the thresholds for the CPU module (values in `CRIME_RE.h`: below implementation 0x23 or equal to 0x27 the full level is 20 and the empty level 0; other implementations 48 and 24), wait for idle (`crmIdleWait`, 4096 polls), write the final `IB_CTL` and flush the bus.

The colour-index TLB (`+0x16e0`) is not cleared by this routine (established as an absence in the function). The reset state of every register is unknown from the kernel: it never reads any of them back before writing.

Pass 3 (established): the only writers of `+0x408` in any object read are `crimeInitHW`, `crimeError` and two sites in crime.o (`0x5204`, `0x5800`, both writing zero); no read of it exists, and `gfxinit` does not contain its address. Correction, pass 7 (established, `ide.IP32` `0xa00e2f68` to `0xa00e2fa8`): the diagnostics do write it, by ORing `0x408` into the engine base rather than loading the address as a constant: their engine initialisation writes 0 to `+0x408`, waits 10 (their microsecond delay routine), then writes both BufMode registers and clears the three frame-buffer TLBs, the same order the kernel uses. The specification's interface-buffer table ends at `+0x400` (PDF 163–164), so the register is not described there. The inference below is unchanged and still rests only on its position before an `IB_CTL` rewrite. The register is now listed in [RE_DECODE.h](../RE_DECODE.h) as `ib_reset`, a 32-bit store (the kernel's store is a single word), role inferred as above.

Inferred: the `+0x408` write is a soft reset or flush of the rendering engine and its interface buffer. Basis: it is the first write of initialisation, and `crimeError` below writes it and then has to reprogram `IB_CTL` (a write-only register), which suggests the reset returns `IB_CTL` to its power-on value. Neither claim is shown by a source here; NetBSD does not name `+0x408` (its `crimereg.h` only has the CRIME control soft and hard reset bits at `0x0400` and `0x0800`, which this routine does not touch).

## Error recovery (`k:crime:crimeError`)

Called when a drain or idle wait times out (`crmSavePP`, `crimePcxSwap`) and when the timeout that guards the wait for the buffer-empty interrupt (input 25) expires (`crimeEmptyWaitTimeout`), established: print a driver warning at level 4, write `+0x408` with 0, delay 10 microseconds, rebuild the control word from the kernel's four threshold variables as `count | stall << 7 | empty << 14 | full << 21` and write it to `IB_CTL`, flush the bus. It does not clear the TLBs, re-run `crimeInitHW`, or touch the shadow record, so state that was queued is lost without notice (inferred from the function's body, which is short and shows no other writes).

## Kernel bulk zero and copy through the MTE

The kernel uses the MTE to clear and copy host memory (`early_mte_zero`, `mte_zero`, `mte_copy`, `mte_set_tlb`, `mte_fifo_wait`, `mte_spin`, `mte_delay` in `kernel.o`, `crime_kernel/disasm/kernel/kernel.text.s`). The MTE reads and writes host memory only through the linear TLBs (established: both source and destination select codes in the mode words below are the linear codes of `MTE.h`).

- Clear (`early_mte_zero`, `mte_zero`; established): mode `0x11` (clear, destination select 4 = linear A, destination ECC bit 1) is written through the start alias (`+0x3800`) after BYTEMASK (`+0x3008`) = -1, FG (`+0x3018`) = 0, DST0 (`+0x3030`) = the start address, DST1 (`+0x3038`) = start + length - 1. Each pass covers at most `0x20000` bytes; the loop repeats with the next chunk. Before each pass it waits for 5 free interface-buffer slots (`mte_fifo_wait`).
- Copy (`mte_copy`; established): mode `0x897` (copy, source select 4 = linear A, destination select 5 = linear B, both ECC bits, 8-bit depth field 0): source in linear A, destination in linear B. It writes SRC0 (`+0x3020`), DST0 (`+0x3030`), SRC1 (`+0x3028`) = SRC0 + n - 1, DST1 (`+0x3038`) = DST0 + n - 1, BYTEMASK = -1, then the mode through the start alias. It waits for 6 free slots first. The chunk is the smaller of the remaining length and what both TLBs mapped.
- Address given to the MTE (established): the SRC and DST words carry the same address the kernel passes in as the host address (no translation by the kernel) and the TLB is loaded to translate that address back to itself; the function takes `address >> 12` as the page number. Inferred: the callers pass physical addresses (the code uses no `kvtophys`, and `early_mte_zero` runs before virtual memory); that these words are plain host addresses and not tile addresses is therefore implied only for linear-select operations. The byte-column and row form of the address word (`docs/mte.md`) is for tile selects and does not appear here.
- Linear TLB loading (`mte_set_tlb`; established): the TLB index is `(page >> 1) & 15`, so address bits 16:13 select one of 16 doublewords at `+0x1700` (A) or `+0x1780` (B). Each doubleword holds two entries, the even page in bits 63:32 and the odd page in bits 31:0, each `0x80000000 | page number`; the mapping covers 32 pages (128 KiB) per load, which is why the chunk is `0x20000`. A start address with an odd page number loads the preceding even page too. The function returns a bit mask of the doublewords it wrote and a byte count (8192 per doubleword) and the caller passes the masks to `crimeRestore` afterwards (see `docs/context.md`). It waits for enough free interface-buffer slots (`mte_fifo_wait`, one per doubleword) before writing.
- Waiting (`mte_fifo_wait`; established): the free-slot test is `64 - ((status >> 18) & 0x7f) >= n`, polling every microsecond, which confirms a 64-entry interface buffer and that status bits 24:18 are the fill level.
- Completion (established from the object code, inferred as to intent): `mte_spin` compiles to a test of `(status < 1)` ANDed with `0x02000000`, which is always zero, so it never waits. The constant is status bit 25, the MTE-idle bit NetBSD names `CRIME_DE_MTE_IDLE` (the OpenBSD driver names the same bit ready; the position is recorded as `RE.status` field `mte_idle`, meaning inferred, in [RE_DECODE.h](../RE_DECODE.h)); the intended wait for it is not effective as shipped. `mte_delay` returns `0xffffff` unconditionally because `crimeLockOut` always returns 1.

## Answers for the MTE rows

- DMA: the MTE has no separate engine for host memory; host transfers are MTE operations with a linear-TLB source or destination (established). Kernel use is above. Whether the MTE reads through the same TLB entries when a rendering primitive is in flight is unknown. Test that would settle it: start an operation with a linear source while a primitive is in flight, change the linear table entry for that page, and see which entry the transfer used (hardware); the document route is the specification's ordering text for the table group (PDF 164-165).
- Interrupts: the kernel registers no MTE-specific interrupt. The only engine interrupts IRIX uses are the interface-buffer empty and full levels (inputs 25 and 26, `CRIME.h`); MTE operations use the same buffer and are paced by `mte_fifo_wait`, not by an interrupt (established as an absence in `k:crime`, `kernel.o`). Whether the hardware raises its own MTE-done interrupt is unknown. Test that would settle it: run a transfer long enough to pass the empty and full levels and read the interrupt status for inputs 25 and 26 (hardware); the document route is the specification's interrupt table, for the sources it lists on those two inputs.
- Reset: no MTE-specific reset is written (established as an absence); the engine-wide `+0x408` write in `crimeInitHW` and `crimeError` is the only candidate (inferred).

## Settled in pass 7

- `+0x408`: every writer (kernel and diagnostics) writes 0 to it first, waits, and then reprograms the interface-buffer control and the TLBs, so it resets the interface buffer and the engine's front end (inferred, as above). Which units it resets beyond that: unknown: no shipped software or published source depends on it, because every writer reloads all state it uses afterwards. Routes tried: [spec] (the interface-buffer table ends at `+0x400`), the 6.5.30 kernel, `ide.IP32`, `gfxinit`, NetBSD, Linux, MAME. Test that would settle it: set state in each unit (a table entry, a mask, a transfer register), write zero to this register, and read each back (hardware, no sweep: one register per unit); the document route is a later specification revision describing the interface buffer reset.
- Reset values of the rendering and MTE registers: unknown: no shipped software or published source depends on them. The kernel, the diagnostics and the X server write every register they use before using it (the kernel order above; `ide.IP32` additionally clears BufMode, the frame-buffer TLBs, screen masks, scissor and window offsets), and no reader samples a register before writing it. Routes tried: [spec] (the rendering chapter's tables give no reset column), the 6.5.30 kernel, `ide.IP32`, the X module, libGLcore, NetBSD, Linux, MAME. A model may reset them to zero. Test that would settle it: read each rendering and transfer register after a power-on reset and before any write on hardware (a bounded read of the registers the specification lists, with the owner's agreement); the document route is a revision with a reset column.
- Linear TLB lookup: the kernel loads the doubleword `(page >> 1) & 15` for every page and never relies on any other doubleword, so a model that indexes by address bits 16:13 without a tag satisfies it (inferred); whether silicon compares a tag: unknown: no shipped software depends on it. Test that would settle it: load a linear table entry for one page, then access another page that shares address bits 16:13 and see whether it translates (hardware); the document route is the specification's linear table text (PDF 164-165).
- MTE ordering: the specification has every committed operation execute in commit order and atomically ([spec] PDF 186), and marks the TLB registers global, which are not updated until earlier work has left the pipeline ([spec] PDF 164-165, tables 7-2 and 7-3). The kernel's `mte_copy` relies on exactly that: it rewrites the linear TLBs for the next 128 KiB chunk without waiting for the previous copy to finish (only for interface-buffer slots, `mte_fifo_wait`). So an MTE operation sees the TLB entries written before it was committed and none written after (established as specification plus driver expectation).
- MTE completion interrupt: the specification's interrupt table has no MTE-specific input; the only engine interrupts are idle, FIFO-empty and FIFO-full, each as an edge (22 to 24) and a level (25 to 27) input ([spec] table 5-5, `CRIME.h`). Whether "idle" includes the MTE: inferred yes, since the MTE is one of the engine's four units ([spec] PDF 160); unknown beyond that: no shipped graphics object unmasks input 24 or 27. Tests that settle it: (1) a document read, the status-register chapter of a later specification revision, for whether the combined idle bit (28) is the AND of the setup, pixel-pipe and MTE idle bits (25 to 27), which would make the idle interrupt cover the MTE; (2) on hardware, unmask input 24 with the engine idle, start one MTE copy and see whether the edge interrupt fires at its completion and not before (one register write, one operation, no sweep).
