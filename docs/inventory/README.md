# Inventory

Everything under this directory is generated by `scripts/inventory.py`; do not edit it by hand. It counts what the in-scope binaries contain and records, for each entry, whether this repository documents it. The summary is at the top of [../coverage.md](../coverage.md).

| File | One row per | Counted from |
|---|---|---|
| `binaries.tsv` | file or archive member in scope | the `files` and `members` blocks of `IRIX_FILES.md` |
| `functions.tsv` | function symbol in each binary | `.symtab`, `.dynsym`, DWARF subprograms and the ECOFF `.mdebug` procedure table, merged by name and address |
| `mmio.tsv` | distinct register offset reached in the CRIME (`0x14000000`), rendering-engine (`0x15000000`), GBE (`0x16000000`) and MACE video (`0x1f100000` to `0x1f280000`, `0x1f400000` to `0x1f800000`) windows | disassembly, see below |
| `tokens.tsv` | distinct (rendering register, constant word) pair stored | disassembly, see below |
| `ioctls.tsv` | graphics ioctl request number | kernel dispatcher constants and `ioctl` calls in user code |
| `spec-registers.tsv` | register in the CRIME 1.5 and GBE (rev 1.1) specifications | the specification register tables, parsed from a text extraction of each PDF |

## Status

- `documented`: a chapter under `docs/` or a header names the entry. For functions, the name appears in backticks in a chapter or anywhere in a header. For register offsets, a header defines the value, a chapter writes it as `+0xOFFSET`, or either writes the full address; an offset inside a specification register whose name the repository documents counts as well (`matched_by` says which). For ioctls, the request number appears in the ioctl, context, GBE, pixel-transfer or memory chapter. For tokens, the word and the register offset (or its specification name) appear within two lines of each other. The `doc` column holds the file and section of the first matches.
- `named-only`: the entry appears only in an index file (`AGENTS.md`, `README.md`, `IRIX_FILES.md`, `docs/coverage.md`, `docs/captures.md`).
- `undocumented`: no match.

Matching is by search, so it can overstate (a name quoted in a chapter that says nothing useful about it) and understate (a chapter that describes an entry without its exact name or offset). A reader who documents an entry writes its exact name, `+0xOFFSET` or request number so the search finds it.

## How register accesses are found

`scripts/inventory.py` disassembles each ELF binary and follows constants through a function: `lui`, `ori`, `addiu`, `sll` and `or` build an address, and any load or store whose effective address falls inside a window above is recorded with the offset from the window base. Register values survive a branch join only when every path agrees on them, and a loop drops the registers its body writes. A store to `offset + 0x800` in the rendering-engine pixel-pipe or transfer-engine groups is the start alias of `offset`; it is counted under `offset` and in `via_start_alias`.

Most code never holds a hardware address as a constant: it loads a pointer from a structure. `scripts/inventory-config.json` lists those pointer fields (`field_pointers`) and the functions that receive a window base as an argument (`argument_pointers`), each with the finding that justifies it. An access through such a pointer is recorded with the `evidence` column naming how the base was known. Accesses whose base the script cannot follow are missing from `mmio.tsv`; this affects the stripped X server modules, which reach the GBE through a kernel-mapped block (ioctl `0x55fc`), the kernel's interrupt code in `kernel.o`, and the video libraries. When you identify another pointer, add it to the configuration and regenerate.

`tokens.tsv` holds only stores whose value is a compile-time constant. Words built from variables (vertex coordinates, colours, addresses) are not rows.

## Ioctls

User-code requests come from the second argument of a call to `ioctl` when it is a constant in the graphics range `0x5200` to `0x56ff`. Kernel requests come from `crimePrivate`, the dispatcher in `crime.a`: it finds cases by a binary search on compare-immediate boundaries and by equality tests against loaded constants. `kernel_evidence` is `handled` for a loaded constant and `boundary` for a compare immediate, which sits next to a case but is not always one; confirm a `boundary` row in the disassembly before relying on it. Requests the X server sends through other libraries are not seen.

## Regenerating

Run `scripts/inventory.py` from the repository root with the MIPS binutils, `dwarfdump` and `pyelftools` of `AGENTS.md` section 5 on the path, after `scripts/populate-root`. Without arguments it rereads the register rows of `spec-registers.tsv` and refreshes every status. To rebuild those rows from the specifications, give it a text extraction of each PDF with a line `=====PAGE n=====` before each page and the layout kept: `--spec crime=FILE --spec gbe=FILE`. The extractions are not committed (the specifications are third-party documents); the sources are the CRIME 1.5 specification, revision 0.3 (2 June 1997), and the GBE specification for revision 1.1 (18 July 1996).

## Limits

- Only the binaries named in `IRIX_FILES.md` are scanned. `os.a` is limited to `tile.o`.
- The function table repeats a function once per binary that carries it (release and debug builds, o32 and N32 builds). `coverage.md` also reports the count by distinct name.
- `spec-registers.tsv` covers the register tables of the CRIME 1.5 specification (CPU interface, memory controller, interface buffer, TLBs, pixel pipe, transfer engine) and the GBE register map. The CRIME status registers at `+0x4000`, the per-field tables and the specification's other chapters are not rows.
- The text extraction of a specification PDF drops rotated text; a table that does not parse shows as missing rows rather than wrong ones.
