# Pixel arithmetic: depth, blending and texel filtering

The arithmetic of the depth stepper and test, the blender and the texel filter of the CRIME rendering engine: bit widths, rounding and the order of operations. Register offsets and field layouts are in [CRIME_RE.h](../CRIME_RE.h).

Labels: **established** (read from the cited source or code), **inferred** (reasoned, with the reasoning), **unknown**. Sources:

- [spec]: the CRIME 1.5 Specification, revision 0.3 (PDF page numbers).
- [hdr]: the register layout headers shipped with IRIX 6.5.5 as the CRIME stack header 22 and the CRIME stack header 21. They declare each pixel-pipe register as a bit-field structure; the field names are cited, the layout restated in our own words.
- [gl]: IRIX 6.5.30 N32 `libGLcore` (`usr/gfx/arch/IP32CRM32`), by unit under `libglcore/asm/` and function. The software rasteriser units under `libglcore/asm/soft/` are the generic OpenGL fallback; they show the formula the library computes when it draws without the engine, not the engine's arithmetic.
- [ide]: the IP32 stand-alone diagnostics, 6.5.30 `stand/ide.IP32` (binary).

## Depth

### Vertex position (the 13.6 field)

- Established ([gl] `crm_astri`, `crm_context`): the library adds a bias of 135168.0 (`0x21000`, that is 4096 plus 0x20000) to every window x and y in single precision, so each value lies in [131072, 262144) where one unit in the last place is 1/64. The bias is part of the viewport centre, so the add happens in the viewport transform itself. **Established (published):** the O2 technical report lists "6-bit subpixel positioning for OpenGL coordinates" and a 4K x 4K address space ([published-sources.md](published-sources.md#1-o2-technical-report-version-10)), which fixes the 6 fraction bits; the report does not describe the bias.
- Established ([gl], no `ctc1` anywhere in the extracted `libGLcore`): the library never changes the FPU rounding mode, so the process default applies. IRIX starts processes in round-to-nearest-even (inferred from the absence of any other setting; not read from the kernel).
- So each vertex coordinate written to Vertex.GL is the window coordinate rounded to the nearest 1/64, ties to even (inferred, from the two facts above). The engine reads bits 18:0 of the stored word as an unsigned 13.6 value holding `coordinate + 4096` (inferred strongly; see the Vertex.GL note in `CRIME_RE.h`).

### Window z and the Zs, dz/dx, dz/dy words

- Established ([gl] `soft/so_xform` `SetDepthRange`, `crm_context`): window z is `scale * z_ndc + centre`, with `scale = 0.5 * (far - near) * M` and `centre = 0.5 * (near + far) * M`; near and far are first clamped to [0, 1], the two products are formed in double precision and stored as single-precision floats, and the per-vertex multiply-add is then single precision (re-read from `SetDepthRange`), where `M` is the depth maximum `0x3fffffff` the CRIME context stores. Window z therefore spans 0 to 2^30 - 1.
- Established ([gl] `crm_astri` `__glCrmFlatZTriangle`, `__glCrmSmoothCIZTriangle`, `__glCrmSmoothRGBZTriangle`, `__glCrmSmoothRGBAZTriangle`): the set-up computes the plane slopes A and B in single precision from the three vertices ([spec] PDF 199, equations 7 to 9), evaluates the start value at the integer pixel corner `(Xs, Ys)` found by clearing the low six bits of the start vertex's 13.6 words, as `Zs = z + A * (Xs - x) + B * (Ys - y)` (two multiply-adds, in that order), multiplies Zs, A and B by 64.0 and converts each to a 64-bit integer by truncation toward zero (`trunc.l.s`). Zs goes to `+0x21c8`, dz/dx to `+0x21d0`, dz/dy to `+0x21d8`.
- Established ([spec] PDF 212-213): the engine steps depth with a 25.12 two's complement stepper, `z(Xs + m, Ys + n) = Zs + m * dz/dx + n * dz/dy` ([spec] PDF 198-200, equation 6). The fragment's 24-bit depth is the stepper value with its 12 fraction bits truncated, then clamped to [0, 2^24). The specification tells the host to add 0.5 to Zs to get rounded rather than truncated depths.
- Established ([gl], same four routines): the 6.5.30 driver does not add that half unit. Zs, dz/dx and dz/dy are stored straight from the truncating conversion. A model must truncate, not round, to match the depths IRIX produces.
- Units, by construction: window z times 64 is 2^36 at the top of the range, so the register value is the 24-bit depth-buffer value (window z / 64) with 12 fraction bits, which is exactly the specification's 25.12 (inferred, from the agreement of the two scales; the clear value below uses the same units).
- Precision (established arithmetic): window z is a single-precision float, which carries 24 significant bits. For depth-buffer values of 2^12 and above, the float has fewer than 12 fraction bits left, so the low fraction bits of Zs are zero; at the top of the range the float's resolution is one depth-buffer unit. The slopes are rounded to single precision before scaling.
- Stepper width and the upper bits (inferred): the driver writes full 64-bit words, but every value it can produce fits in 37 bits (sign plus 24 integer plus 12 fraction). Whether silicon keeps more than 37 bits is unknown: no shipped software or published source depends on it. Test that would settle it: write a stepper with bits above 36 set and read back through the first fragment's colour or depth; the document route is the stepper register tables, for the stated width of each stepper.
- Where the stepper samples (inferred): Zs is the plane's value at the integer corner below and to the left of the start vertex, and the stepper moves in whole-pixel steps from there, so the depth of pixel (x, y) is the plane evaluated at the integer point (x, y), not at x + 0.5, y + 0.5. The specification says pixels are sampled at their upper left corner ([spec] PDF 198), which fits sampling at the integer point. No source states whether the engine adds a half-pixel step before the first fragment; the driver supplies no half-slope term, which also suggests it does not.

### Clamping (established, [spec] PDF 212)

After truncation the integer part is clamped to [0, 2^24): negative results become 0 and results of 2^24 or more become 2^24 - 1. The specification states the range but not the mechanism; for colour it describes a test of the top two bits of a 9-bit result ([spec] PDF 200-201), and whether depth uses an equivalent top-bits test (which would wrap results more than 2^24 out of range) is unknown: no shipped software or published source depends on it, because the driver's planes stay inside the clip volume. Test that would settle it: step a depth value past 2^24 and below zero in a one-pixel span and read the depth buffer; a document route is the depth stepper text in the specification beside its colour clamp text (PDF 200-201).

### The depth buffer and the test

- Established ([gl] `crm_pixel`, see `docs/pixel-transfer.md`): depth sits in bytes 2:0 of the 32-bit depth/stencil pixel and stencil in byte 3.
- Established ([spec] PDF 213, table 7-25): the test compares the fragment depth zs with the stored zd using the function in Depth.func bits 27:25 (NEVER, LESS, EQUAL, LEQUAL, GREATER, NOTEQUAL, GEQUAL, ALWAYS, codes 0 to 7). Both operands are 24-bit values in [0, 2^24) after clamping, so the comparison is an unsigned 24-bit compare (inferred, by construction).
- Established ([hdr] `CrmDepthMode`): Depth.func is laid out as 4 reserved bits (31:28), `func` (27:25), `enTagClear` (24) and `clear` (23:0). The driver sets bit 24 only when depth testing is on and the drawable has no depth buffer, the stencil-only case already recorded in `CRIME_RE.h` ([gl] `crm_depth` `__glCrmPassDepthFunc`). The header's name says bit 24 enables a "tag clear"; what the engine does with it is unknown: no shipped software or published source depends on more than the driver's one use.
- Established ([gl] `__glCrmPassDepthFunc`): the clear value in bits 23:0 is `(int)(M * clear_depth) >> 6` in double precision with truncation, masked to 24 bits, so `glClearDepth(1.0)` gives `0xffffff`. It uses the same units as the Zs integer part.

## Blending

- Read ([spec] PDF 208-210, equation 12): with DrawMode bit 10 set, each of R, G, B and A becomes `Cs * S op Cd * D`, where op is Blend.func bits 11:8 (ADD 0, MIN 1, MAX 2, SUBTRACT 3, REVERSE_SUBTRACT 4) and MIN and MAX ignore the factors. The factor codes (Blend.func bits 7:4 source, 3:0 destination) are the specification's tables; [hdr] the register layout header lists the same values, with SRC_ALPHA_SATURATE as source code 12. Blending applies to RGB(A) pixels only, after the antialiasing coverage stage and before dithering and the logic op ([spec] PDF 208-210).
- Established ([gl] `crm_attrib` `__glCrmPassBlendFunc`; see `CRIME_RE.h`): on a drawable without alpha bits the driver rewrites DST_ALPHA to ONE and ONE_MINUS_DST_ALPHA and SRC_ALPHA_SATURATE to ZERO, so the engine never reads a missing destination alpha.
- The operands (established): the source colour reaching the blender is 8 bits per component. Flat colours are truncated from the float colour by the driver; smooth colours come from 9.12 steppers whose fraction is truncated and whose 9-bit integer is clamped to [0, 255] ([spec] PDF 200-201). The triangle set-up adds no half unit to the colour starts either ([gl] `crm_astri`: each start is stored as `trunc(c * 4096)` with no add after the conversion), so a smooth colour is truncated unless the vertex colour already carries a bias, which no routine read here adds. Destination components are the 8-bit fields of the stored pixel.
- The intended formula (established for the software path only): the generic software blender ([gl] `soft/so_blend`, `__glDoBlend_SA_MSA`, `__glDoBlendSourceSA`, `__glBlendSpan_SA_MSA`) works on single-precision floats: it scales alpha by the reciprocal of the alpha range (gc+30812), forms the factors in float, and computes `Cs * f + Cd * (1 - f)` (for the SRC_ALPHA, ONE_MINUS_SRC_ALPHA pair) as a multiply-add; conversion to the stored integer happens later in the span store. This is the OpenGL formula, not the engine's.
- Unknown: no shipped software or published source depends on it: how the engine multiplies an 8-bit component by an 8-bit factor (whether a factor of 255 means exactly 1.0, the width of the product and the rounding of the result), and whether ADD and SUBTRACT saturate or wrap. The only factor conversion the specification mentions for this engine is fog's: an 8-bit factor above 128 is incremented by one ([spec] PDF 206, whose sentence breaks off at "so that"). That 255 therefore becomes 256 and that the 1.8 product with 256 returns the colour unchanged is inferred from the 1.8 format, not stated. Whether the blender uses the same rule is unknown; it is the rule a model would most plausibly reuse (inferred, weakly, from the shared design). Saturating ADD and SUBTRACT to [0, 255] is what OpenGL requires and what the software path does through its clamped store; the specification is silent. Settling test: a capture of the engine blending known 8-bit source and destination values (factor 255 and 128, ADD and SUBTRACT overflow cases) read back from the frame buffer; the specification's missing sentence at PDF 206 would also settle the factor rule.

- Established absence ([spec] Table 7-20, PDF 208-209): the source factor table names SRC_ALPHA_SATURATE but gives no factor. The destination factor table (Table 7-21) has no such code. Equation 12 therefore has no defined saturate factor. The specification gives no clamp for the ADD and SUBTRACT results either.

### Dither

- Established ([spec] section 7.3.7.13, whose body is "TBD"; the DrawMode field table lists the enable): DrawMode has a dither enable bit. `CRIME_RE.h` records it as bit 8 from the drivers, against the specification's bit 9 (the drivers are followed). Logic operations act on the colour after dithering ([spec] section 7.3.7.14), so dither comes before the logic op in the pipeline.
- Established (absence, searched 2026-11-10 over the pixel-state register list in `CRIME_RE.h` and the register scans in `docs/opengl.md`): no pixel-state register holds a dither matrix, offset or seed, and the driver library writes only the enable bit (`__glCrmEnableDither`). The matrix is therefore fixed in the engine.
- Unknown: no shipped software or published source depends on it: the matrix values, whether it is indexed by window or screen position, and which bit width each format drops. The technical report limits dithering to 3:3:2 and 5:5:5 targets ([published-sources.md](published-sources.md)). What would settle it: render a flat mid-grey into a 16-bit window on a real O2 with dither on and read the frame buffer back; the repeat period and the pattern give the matrix (hardware only).

Routes tried for the blend arithmetic: the specification (equation 12 and the factor tables only; its dithering section is "TBD"); [hdr] (field layout and codes, no arithmetic); [ide] (the 6.5.30 `ide.IP32` strings: the visual tests draw flat points, lines and rectangles and compare a CRC of the frame buffer; none enables blending, depth, fog or texture); [gl] hardware set-up (selects codes only) and software path (float OpenGL formula); Linux `gbefb`, NetBSD `crmfb`, MAME `crime.cpp` and GXemul the emulator-side device model source unit 2 (none models the pixel pipe's blender, depth or texture stages). Not read: the O2 libraries of IRIX 6.3; they cannot change the answer, because the blend is computed in the engine after the driver has selected codes. Published sources, searched 2026-10-29 ([published-sources.md](published-sources.md)): the O2 technical report, the unified-memory and digital-media white papers, the graphics-implementations paper and the one patent on the chip give the order of operations (destination read in the colour pipeline, depth and stencil discard first) and the 8-bit operand width, and no product width, rounding or saturation rule; the dither is limited to the 3:3:2 and 5:5:5 formats, with no matrix.

## Logic ops

- Established ([spec] PDF 210-211, Table 7-23, section 7.3.7.14): when DrawMode's logic-op enable is set, a bitwise operation combines the source colour, after dithering, with the destination colour read from the frame buffer. The sixteen operations, with `s` the source and `d` the destination, are CLEAR `0`, AND `s&d`, AND_REVERSE `s&~d`, COPY `s`, AND_INVERTED `~s&d`, NOOP `d`, XOR `s^d`, OR `s|d`, NOR `~(s|d)`, EQUIV `~(s^d)`, INVERT `~d`, OR_REVERSE `s|~d`, COPY_INVERTED `~s`, OR_INVERTED `~s|d`, NAND `~(s&d)` and SET `1`.
- Established ([spec] section 7.3.1.17): the LogicOp register's field table is empty, so the numeric code for each operation is not given in the specification. `CRIME_RE.h` takes the codes from the drivers.
- Logic ops apply to both colour-index and RGBA pixels ([spec] section 7.3.7.14).

## Alpha test

- Established ([spec] PDF 207, section 7.3.7.11): the alpha test compares the fragment's alpha after antialiasing coverage has been applied. It applies only to RGB(A) pixels, is enabled by DrawMode bit 11, and discards the fragment when the comparison fails. The driver's glAlphaFunc reference is scaled to the 8-bit field as described in [opengl.md](opengl.md).
- Established ([spec] PDF 180, AlphaTest register; PDF 207, table 7-19): the reference is bits 7:0, an 8-bit value, and the function is bits 11:8. Bits 31:12 are reserved. The function codes are NEVER 0 (false), LESS 1 (`alpha < ref`), EQUAL 2 (`alpha == ref`), LEQUAL 3 (`alpha <= ref`), GREATER 4 (`alpha > ref`), NOTEQUAL 5 (`alpha != ref`), GEQUAL 6 (`alpha >= ref`) and ALWAYS 7 (true).
- Unknown: function codes 8 to 15 have no entry in the specification's table, so their behaviour is not known. No shipped software or published source sets one.
- Unknown: the order of the alpha test against the depth and stencil tests. The specification gives the coverage-then-alpha-test order and says nothing about depth or stencil relative to it.

## Texel filtering

### Coordinates reaching the filter

- Established ([spec] PDF 203-204, figure 7-15 and table 7-17): the engine steps s/w, t/w and 1/w as 36.12, 36.12 and 18.12 values, divides, maps (s, t) to (u, v), computes a level of detail, looks texels up and filters them.
- Established ([gl] `crm_astextri` `__glCrmFillTriangle`): the driver scales s/w and t/w by 2^43 (or 2^39 for a coordinate flagged in `+0x2134`) and 1/w by 2^29, truncates each start and slope toward zero, and then adds 2048 to each of the three starts (`+0x2120` sq, `+0x2128` tq, `+0x2130` q) but not to the slopes. 2048 is one half in the steppers' 12-bit fraction, which is inferred to be the same half-unit adjustment the specification recommends for colour and depth starts ([spec] PDF 201, 212); the specification does not mention it for the texture steppers. If the engine truncates their fractions, the added half unit rounds to nearest. The driver does not do so for depth or colour (above).
- Established ([hdr] `CrmTextureReg`): the 32-bit word at `+0x2134` is named `stShift`, which agrees with the reading in `docs/opengl.md` that its two bits select a four-bit shift of the s and t steppers.
- By inference ([gl] scales, as in `CRIME_RE.h`): after the divide a texture coordinate of 1.0 is 2^14. Texture.format shifts it right by `10 - log2(size)` (the `uShift` and `vShift` fields, so named in [hdr]), leaving a texel coordinate with 4 fraction bits, and the index masks keep `log2(size) + 4` bits, which implements GL_REPEAT by masking. The maximum size is therefore 1024 texels per side, which [hdr] the register layout header states as a maximum level of detail of 10 and [spec] PDF 202 as 1k by 1k.
- Established ([gl] `__glCrmFillTriangle`): the driver applies no half-texel offset to s or t for linear filtering; no constant 0.5 enters the set-up.

### Level of detail

- Established ([spec] PDF 204, figure 7-16): the engine takes the four differences of u and v between a fragment and its right and upper neighbours and computes `rho = max(du/dx, dv/dx, du/dy, dv/dy)` and `LOD = log2(rho)` (the magnitudes are implied, inferred). This is not the generic software formula: [gl] `soft/so_texture` `__glComputePolygonRho` sums squared u and v derivatives per axis before taking the larger, the OpenGL length form.
- Unknown: no shipped software or published source depends on it: the precision of the LOD (integer only or with a fraction), how the fraction weights the two levels in the MIPMAP_LINEAR modes, and the magnification-to-minification switch point. The specification's sections on texel look-up and on minification and magnification filtering are "TBD" ([spec] PDF 205). Settling test: a capture of the engine texturing a mipmapped checker with a known scale ramp, read back to see where the level switches and how the fraction blends; no document or binary read is expected to settle it.

### Filter weights

- Read ([spec] PDF 202, [hdr] the register layout header): the filter codes are NEAREST 0, LINEAR 1, NEAREST_MIPMAP_NEAREST 2, LINEAR_MIPMAP_NEAREST 3, NEAREST_MIPMAP_LINEAR 4, LINEAR_MIPMAP_LINEAR 5 (Texture.mode bits 9:7), with magnification NEAREST or LINEAR in bit 6.
- Inferred (from the 4 fraction bits above): a bilinear weight has at most 4 bits, sixteen steps per texel.
- The intended formula (established for the software path only): [gl] `soft/so_texture` `__glLinearFilter2` computes `u = s * width - 0.5` (after clamping s for the clamp modes), `i0 = floor(u)`, `i1 = i0 + 1`, `a = frac(u)`, likewise `b` for v, fetches the four texels as floats and returns `(1-a)(1-b) t00 + a(1-b) t10 + (1-a) b t01 + a b t11` in single precision, with no quantisation of the weights. `__glLMLFilter` filters both levels and blends them as `(1 - f) * level_a + f * level_b`, where f is the fraction of the level of detail (`__glFrac`), again in float.
- Unknown: no shipped software or published source depends on it: whether the engine applies the half-texel offset itself (the driver does not, so a conformant engine must), how the 4-bit weights are formed (truncation of the coordinate fraction is the plain reading), the order and width of the products and the rounding of the filtered 8-bit components, and the arithmetic of texture application (MODULATE, DECAL, BLEND, REPLACE; [spec] PDF 205 names them only). Settling test for the filter arithmetic: draw a bilinear-filtered rectangle from a one-row texture whose two texels are `0x00` and `0xff`, stepping the s coordinate by one sixteenth of a texel per pixel across the span, and read the pixels back. Where the ramp starts shows whether the engine applies the half-texel offset, the number of distinct intermediate values shows the weight width (sixteen if the weights have 4 bits), and the values at exact eighths show whether the product truncates or rounds. This is a hardware test and needs the hardware proposal the project requires; no document or binary read is expected to settle it.

Routes tried for the filter: as for blending, plus the generic software texture unit and the format and mode headers. A model that truncates the 4-bit fractions, weights the four texels with products of those fractions and truncates the result is consistent with every established field, but it is a choice, not a finding. Published sources, searched 2026-10-29 ([published-sources.md](published-sources.md)): the technical report says the divide is floating point and the level of detail per pixel, and no source gives a weight width; a predecessor patent gives a level fraction linear in the maximum derivative (`(LOD >> fine) - 1.0`), a candidate for the unknown level-of-detail fraction, inferred and unconfirmed for this chip.
