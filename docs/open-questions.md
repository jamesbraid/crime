## Silicon tests for the hardware-only unknowns (2026-11-10)

Every item below was left open because no shipped software, specification or published source depends on it. Each gets the smallest test on a real O2 (CRIME and GBE named in the chapters) that gives a different observation under each candidate answer. They are recorded, not scheduled; none is needed to read the shipped software. The test is written so that a run on a machine of any CRIME or GBE revision records the revision words first (`CRIME.id` at `0x14000000`, `GBE.ctrlstat` chip revision), because the answers are per revision.

- **Does the linear TLB compare a tag?** ([reset.md](reset.md)) Load linear-A doubleword 3 with a valid entry for tile T. Run a transfer-engine read of one tile through linear page number 3, then through page 19 (same address bits 16:13, different upper bits), into the same destination, and compare the destination with the tile contents. Page 19 returning T means the lookup is indexed by bits 16:13 alone; an untouched destination plus an error bit in the status or CPU-error register means a tag is compared.
- **What an invalid or out-of-range rendering TLB entry does** ([memory.md](memory.md)). Clear the valid bit of one frame-buffer TLB entry, fill a one-pixel rectangle through it, and then read the pixel back through a valid mapping of the same tile. Record (a) whether the pixel changed, (b) the `0x4000` status word and (c) both error status registers. A changed pixel means writes are not dropped; unchanged with a status or error bit separates dropped from reported. Repeat with a read (`glReadPixels`-style transfer) to learn what a read returns.
- **Does the transfer engine raise its own completion interrupt, and does "idle" include it?** ([reset.md](reset.md)) Unmask CRIME interrupt inputs 22 and 25 only, with the rendering FIFO empty. Start one 1 MiB memory-transfer fill and poll `0x14004000` for the idle bits while sampling `CRIME.intstat` in a tight loop. If bit 22 or 25 sets before the fill's destination reads back complete, idle excludes the engine; if it sets only after, idle includes it. Repeat with inputs 23 and 24 unmasked to see whether any of them ever sets for a transfer.
- **What a write to the transfer engine's null register does** ([mte.md](mte.md)). Program a fill (mode, destination, one tile) through the non-start addresses, then write the null register at its plain address `0x15003070` and read the tile back, then write it again at its start alias `0x15003870` and read the tile back again. Memory changed after the first write means any write to the register starts the operation; changed only after the second means the start alias commits the queue (the reading the pixel-pipe twin suggests); unchanged after both means the register has no effect on a fill.
- **Reset values of the rendering and transfer registers** ([reset.md](reset.md)). From a cold reset, before any write, read every readable register of the CRIME, rendering and transfer blocks with 64-bit loads and log the values; for write-only registers, write all-ones, read nothing, and run a one-pixel fill so a missing reset becomes visible as a fill with the wrong colour mask. Do this twice, once after power-on reset and once after a soft reset through `CRIME.control` bit 10, because the two resets may differ.
- **Whether a line interrupt fires when its line is rewritten to the line the beam is on** ([gbe.md](gbe.md)). Run a stable timing. Read `VT_XY` until the vertical count is L, write `VT_INTR01.line0 = L` at once, then record whether interrupt input 16 sets in `CRIME.intstat` before the count reaches L + 1. Repeat after the horizontal count has passed half the line, and with `line0 = L - 3` written after the beam is already on line L (behind the beam). Three outcomes: fires in the line; fires one frame later; never fires in that frame.
- **What bit 20 of the dot-clock word does** ([gbe.md](gbe.md)). With a CRT timing running, write the word with bit 20 cleared and the pixel-clock fields unchanged, observe the pixel clock at the DAC (and `VT_XY` advance), set bit 20 again, and time how long the clock takes to return stable. A stopped clock with `VT_XY` frozen supports "bit 20 runs the PLL or its output"; a running clock with a drifting phase after the set supports "it gates only the output".
- **Which counter the flat-panel enable compares** ([gbe.md](gbe.md)). Write `FP_DE` with off 300 and on 100 with a known CRT timing running, probe the flat-panel enable pin and count transitions per frame. Two per line means the horizontal counter, two per frame the vertical one.
- **Does a rejected coherent load set CPU error bit 2?** ([memory.md](memory.md)) With the error status clear, issue a coherent read to a physical address in a range the CRIME specification marks reserved in its CPU address map (PDF 47 to 52), catch the bus error, and read `CRIME.cpu_error_stat` (`0x14000048`, or `0x14004048` on a part that has it). Bit 2 set means the illegal-address status accompanies the rejection; clear means only the processor bus error is raised.
- **What answers the high RAM alias at `0x20000000`** ([memory.md](memory.md)). Write a distinct 64-bit tag at every 64 MiB step of the full window (`0x40000000` upwards) up to the installed memory, flush the caches, and read the tags back at every 64 MiB step of the high alias. The permutation shows whether the alias is the upper half of the full window, the lower half, or a repeat; reading beyond installed memory shows the reserved-range response.
- **A primitive in flight when the engine's context is reloaded** ([context.md](context.md)). Start a large smooth-shaded triangle, wait for the FIFO level to read non-zero, and write the interface-buffer reset (the word at `0x15000408`, value 0) then a different 4-pixel fill. Compare the memory with each of three images: the triangle complete, the triangle cut off at some span, and the triangle absent. This also settles whether `+0x408` resets more than the front end.
- **Performance and contention leads** (fill rate, triangle rates by mode, readback cost, scan-out contention, uncached/cached ratios, texture upload cost, R5000 against R10000 latency, pbuffer/MTE/scan-out stress). Each is a timing claim, so one protocol covers them: on a 64 MB-or-larger machine in one fixed video format, run the rendering call 10,000 times between two reads of the CRIME timer or the CPU count register, repeat in three video formats (640x480_60, 1280x1024_60, 1280x1024_75) so scan-out load varies while the call is fixed, and report the per-call time with its spread. A claim is supported only if its stated ratio holds within the measured spread at every video format.
- **Silicon revisions of VICE and of the early R10000 memory interface** (the TRE/DX pairing, the "Juice" revision registers). Read `CRIME.id`, the VICE identity register and `hinv`'s revision strings on at least one machine of each string and tabulate; behaviour differences need the same MPEG-1 decode program run on two parts and the output compared bit for bit.
