# X module functions by role

What the routines of the IRIX 6.5.30 X module `usr/lib/X11/dyDDX/crm.so` do, by group. Sources: the module's symbol table (840 symbols), the assembly listing `ddx/asm/crm/crm/crm.s`, and the public X11 sample server whose names the module reuses. Labels: **established** where the code was read; the per-routine evidence is in [Derivations from the code](#derivations-from-the-code) below, and earlier chapters hold the detailed sequences (the copy, fill and swap sequences of [mte.md](mte.md); the colour-map and ID code of [gbe.md](gbe.md)). The group tables give each group's role; where a routine's role rests on its name rather than on what its code does, its derivation row says so and the role is **inferred**. The module is stripped of local symbols, so file-local routines carry a compiler suffix (two dots and letters) in the lists.

## Register access

How the X module reaches the rendering engine and GBE, and which registers each hardware routine writes. Sources: the IRIX 6.5.30 `crm.so` disassembly (`objdump -d`), its dynamic symbol table and MIPS GOT (`readelf -A`, canonical `$gp` `0x5b0ea0`), and the kernel's `crime.o` (`crimeMapGfx`, `crime_init`). Labels as above.

### The pointer chain

- Established (`crmKernInit`, `crm.so` `0x48a090`): the module allocates a 0xda0-byte screen private record (`Xalloc(3488)`), stores it in the screen's private array, `pScreen->devPrivates` at screen record `+0x1b4`, at the slot named by the small-data global `crmScreenPrivateIndex` (`0x5aa0f8`, `$gp - 28072`), and also in a module table. It then calls the server's `irixKernInit`, which returns the user address of the graphics mapping; the module stores that address at private `+0x0` and the address plus `0x5000` at private `+0x8`.
- Established (`crimeMapGfx`, `crime.o`): the kernel maps five pages of the rendering engine (board record `+0x78`, the KSEG1 pointer to `0x15000000`) at the start of the mapping and, for the owning process only, `0x81` pages of GBE (board record `+0x80`, which `crime_init` fills from the second word of the board table, the GBE base) at `+0x5000`. So private `+0x0` is the rendering engine at offset 0 and private `+0x8` is GBE at offset 0. The five pages cover `0x15000000` to `0x15004fff` (translation, pixel state, transfer engine and status groups); the GBE pages cover `0x16000000` to `0x16080fff`.
- Established: private `+0xc` points to the module's shadow record. Every store to a pixel-state register is paired with a store of the same value to the shadow at the register offset minus `0x2000` (for example `+0x2008` and shadow `+0x8`, `+0x2040` and shadow `+0x40`; `crmSetSmask`, `crmSolidPolyFillRect`).
- Established, the access pattern: a hardware routine loads `crmScreenPrivateIndex`, shifts it left by 2, adds it to the word at `+0x1b4` of the screen record, loads the private pointer from that slot (displacement 0), and then loads the rendering pointer from displacement 0 of the private record (`crmSolidPolyFillRect` `0x43d230..0x43d260`). Stores then use the register offset as the displacement (`sw $11,8200($18)` is BufMode.dst `+0x2008`); start-alias stores add `0x800` to the address with `ori` first (`+0x2070 | 0x800`, `0x43d334..0x43d340`).

### How the register scan follows the pointer chain

Established (config rule `screen private record` in `scripts/inventory-config.json`, replayed over `crm.so` 6.5.30): the scan follows the chain above, not only the first argument of `crmSetSmask`. A load at screen record `+0x1b4` gives the private array; the slot number loaded from `crmScreenPrivateIndex` (`gp - 28072`, loaded through `$gp`, `$at` or a register holding a copy of it, depending on the routine) is scaled by 4 and added; the private record is loaded from slot word 0; private `+0x0` is the rendering-engine mapping and private `+0x8` the GBE mapping. The slot number is part of the rule, so a record fetched from the same array type with another module's slot number is not mistaken for the register mapping. The module reads other owners' records the same way: `crmResetXvc` (slot number held behind a pointer, `gp - 29112`) walks an array of 0x1f8-byte entries whose fields at `+0x144` and `+0x33c` it clears, and `crmAllocatePbuffer` reads a word at `+0x24` of a record from the slot named by `gp - 28792`. Both look like register sites to a scan that checks only the shape of the chain, and neither is one.

Established, the result on `crm.so`: 2294 rendering-engine sites at 36 offsets in 51 functions and 82 GBE sites at 9 offsets in 10 functions (`+0x10018`, `+0x54408`, `+0x58000`, `+0x70004`, `+0x70008`, `+0x7000c`, `+0x70010`, `+0x78000` and `+0x78004`). A cross-check with a decompiler (every load and store folded to a base expression, restricted to this chain) finds the same sites except the unrolled and delay-slot stores that it attributes to the branch address, and it misses sites in functions it cannot decompile. Stores through a frame pointer set to the stack pointer plus a constant (`crmZeroPolyArc` spills the rendering pointer at `-656($30)`) address stack slots like stack-pointer stores, so those are followed too.

Why a field rule would not do: the rendering pointer is two displacement-0 loads away from the screen record, and a field rule at displacement 0 would also type the private pointer itself (and every other displacement-0 load in the same routines, such as the graphics-context private) as a register window. The first argument of `crmSetSmask` is still configured as an argument base: all 23 calls in the module load it from private `+0x0` (checked call by call, including the delay-slot moves in `crmSolidPolyFillRect` and the frame-pointer spill at `-656($30)` in `crmZeroPolyArc`). Its eight sites are ClipMode `+0x2010` (three stores) and the screen masks `+0x2020` to `+0x2040`.

### `crmSetSmask` and the ClipMode words

Established (`crm.so` `0x58a930`; arguments: rendering pointer, shadow pointer, list of 64-bit masks, count n): with the small-data flag `use_cid` (`0x5aa638`) clear, it stores the n masks (n = 1 to 5) into `ScrMask` `+0x2020` upward, last mask first, as 64-bit stores, and writes ClipMode `+0x2010` from a table indexed by n (0 to 5) in `.rodata` at `0x5a2400`: `0x0`, `0x21`, `0x63`, `0xe7`, `0x1ef`, `0x3ff`, the same per-rectangle enable bits the kernel's `crimeValidateClip` uses ([context.md](context.md)). With `use_cid` set it writes ClipMode `0x800` (clip-ID test only), or `0xc00` (clip-ID test and clip-ID map select) when `use_cid` is 1, keeps the masks unused, and when the mask list differs from the cached one rebuilds a region and draws the clip-ID plane through `crmDrawCID` with `use_cid` as the map selector.

## Visual and depth tables (crm.so)

### GLX capability tables (crm.so)

Read in the 2026-11 pass from the `.data` objects and their relocations in `usr/lib/X11/dyDDX/crm.so` (6.5.30). Each set of the four frame-buffer configurations has a table of capability groups, one group per visual record in the same position, built from 16-byte entries.

- Established (data, relocations): a capability entry is four words. Word 0 is a pointer to the capability's name string (a dynamic relocation against a string exported by the server), words 1 is zero in the file, word 2 is a value and word 3 is a flag. Each group ends with an entry that has no name pointer and the words `0 0 1 0`. The tables are `gbeCapabilityInfo16`, `gbeCapabilityInfo16db`, `gbeCapabilityInfo24`, `gbeCapabilityInfo24db` and the `ar` set of the same four (2064, 2800, 4416 and 5072 bytes), plus the two non-visual tables below. The group counts equal the visual counts of the sets (12, 16, 26 and 29), and groups and visuals agree in position: the byte-reversed 24-plane TrueColor visuals are the groups that list no OpenGL capability (`24` visual 20 lists nothing, `24db` visual 18 lists nothing and visual 23 lists only the display-buffer pair), and the StaticColor and DirectColor visuals are the groups that hold only a colour-map group size. That agreement is the evidence for the pairing (**inferred** for the pairing, established for each table's content).
- Established (the consumer, `Xsgi`: `nmbxLookupCapability` at 0x101ffee0 and `ProcNMBX_GetVisualCapabilities` at 0x101ce5c0): the server walks the entries of one visual comparing word 1 with a name atom, so word 1 is the atom the server stores when it registers the names at start-up. The capability query reply copies (atom, value) pairs, words 1 and 2 of each entry. Word 3 is read by neither routine; its role (it is 1 for depth, stencil, alpha, accumulation and nothing else) is **unknown**; the routes are the enable and release requests of the same extension and the registration routine, to find a reader of that word.
- Established (values): depth 0x18 and stencil 8 where a visual has them (24 plus 8 bits), accumulation 0x40 with 0x10 for each of four components, colour sizes 3-3-2, 5-5-5, 8-8-8 and 10 in the non-visual tables, alpha 1 on the 5-5-5 pairs and 8 on the 8-8-8 pairs that list it. `MaxDisplayBuffers` and `BestUpdateAction` are always 2 when listed (54 entries, always together). `FrameBufferLayer` is 1 and `TransparentPixel` 0 on one 8-plane PseudoColor visual of every set (eight entries). The entries whose value is zero in the file (OpenGL capable, pbuffer capable, stereo, hardware RGB, transparent pixel) carry their meaning by being listed, not by the value (**inferred**: a value of zero cannot mean "not OpenGL capable" on visuals the server offers to GL clients). A scan of the text of `crm.so` for global-offset-table loads of the table addresses found none, so the tables are reached only through the screen-information record at 0x5b2390 (**inferred**; the scan covers the 32-bit load forms only).
- Established (which sets list stereo): the `Stereo` capability appears in the two 32-bit sets only, four times in each (`24` and `24db`, and the same four in the `ar` copies), and never in `16` or `16db`. In `24`, the stereo entries are on 12-plane PseudoColor visuals 10 and 11 (without and with depth and stencil) and on 15-plane 5-5-5-1 TrueColor visuals 18 and 19; none of them lists a display-buffer count. In `24db` the same two kinds carry stereo and `MaxDisplayBuffers` 2 together (visuals 10, 11, 16 and 17). No 8-plane or 24-plane visual lists stereo in any set.
- Inferred (from the two preceding facts): a visual that lists both stereo and two display buffers is the quad-buffer stereo form, which then exists only in the 32-bit configuration with software double buffering; the 16-bit configurations list no stereo visual of any kind in this table. A published account that quad-buffer stereo passes in 16+16 as well is not supported by the static tables; whether the server adds or removes a stereo entry at run time (for the two stereo video formats) was not read, so the table is the advertised maximum and the account is not contradicted for run time.
- Established (display buffers by set): in `16` the 8-plane PseudoColor and 3-3-2 visuals list two display buffers (visuals 0, 1, 3 and 4) and the 5-5-5 visuals do not. `16db` adds two on the two 12-plane visuals 8 and 9 and two on the 5-5-5 visuals 14 and 15. In `24` only 12-plane (8 and 9) and 15-plane (16 and 17) visuals list them. `24db` lists both forms of the 24-plane visuals: visuals 19 to 22 with one buffer and 24 to 27 with two (the byte-reversed visual 23 lists the pair alone). The `db` sets therefore add double-buffered siblings of the single-buffered visuals, which fits the `crmInit` message about software double buffering (**inferred**). Depth and stencil are listed in the second visual of each pair, so paired visuals differ only in that.
- Established (the two silicon families): the `gbe` and `ar` tables are identical except for the colour-map group size of the first three groups of each set, 5 in `gbe` and 6 in `ar`. The tables are chosen by the GBE revision, as the window and colour-map tables are (see [gbe.md](gbe.md)). What the number counts is **unknown**.
- Established (the non-visual tables): `crmNonVisualCapabilityInfo16` (704 bytes, four groups) and `crmNonVisualCapabilityInfo24` (336 bytes, three groups) list pixel-buffer formats, not visuals. The 16-bit table has 8-8-8-8 with and without depth and stencil, then single-component 8-bit and 10-bit formats; the 32-bit table has the two single-component formats and a 10-10-10-10 format. `crmNonVisualPbufConfInfo16` and `crmNonVisualPbufConfInfo24` (64 and 48 bytes) are 16-byte records of the words 1, 0 or 1, 0 or 1, and a byte in the top of the last word (0x02 or 0x01); the fields are **unknown** and need the pbuffer-configuration builder in the server to read. The pixel-buffer size computation behind the largest-pixel-buffer attribute was not reached; the tables hold no size.
- Unknown, with the discriminating test: whether the server can ever report a stereo visual without a stereo video format loaded. Test: on a 32-bit configuration, list visuals with the monitor in a non-stereo format, then switch to `1280x492_120s` and list again; a changed count shows run-time editing of these entries.

Graphics-driver requests are named after their kernel handlers in [ioctls.md](ioctls.md). Requests 102 to 104 are the generic board requests of the shipped public header `/usr/include/sys/gfx.h`. Requests from 1000 (`0x3e8`) up are resource-manager commands from the dispatch table in [ioctls.md](ioctls.md).
- Register writes are stores through the rendering pointer described in [The pointer chain](#the-pointer-chain), each paired with a shadow store at the register offset minus `0x2000`. A routine counts as writing registers only when it stores to the drawing mode (`+0x2018`), the primitive (`+0x2060`) or the transfer engine's mode (`+0x3000`). That rule keeps out unrelated records with large offsets, such as the audio state of the bell routines. The register names are in [CRIME_RE.h](../CRIME_RE.h) and [MTE.h](../MTE.h).
- Calls and callers are direct calls resolved through the offset table, leaving out C-library and allocation calls. Each row names at most one callee and one caller; the full call lists come from the same disassembly.
- "Reports failures with its own message" means the routine passes a string from the module's read-only data to `ErrorF`, `FatalError` or `perror`. The messages are not quoted here.
- Routines read by hand have a fuller description in their row. Those include the colour-map FIFO stores, the cursor control write and the screen-wrapper hooks of the `rrm` routines.

Negative result, established over the same disassembly: none of the 165 `mi`, 165 `nfb`, 218 `cfb`, 59 `mfb` and 20 `SDB` or `xdr` routines sends an ioctl or writes the drawing-mode, primitive or transfer-engine mode registers. The sample-server layers draw into memory only. The one call from them into the hardware layer is `rrmValidateCID`, called from the `nfb` layer. Their roles in the table above stay inferred from the sample server's names.
