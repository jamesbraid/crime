# VICE: the imaging and compression engine

VICE (video, imaging and compression engine; the product literature calls it ICE) is the O2's image-processing ASIC. It sits on the CPU bus beside CRIME, holds a small signal processor for pixel arithmetic, a bitstream processor for variable-length codes and two DMA channels that read and write system memory through a 64-entry translation buffer. The CRIME specification gives it the window at `0x17000000` and interrupt input 31; the shipped software that drives it is `libvice.so` and the image-converter plug-ins listed in [binaries.md](../../evidence/binaries.md). The specification below is the first register-level source this repository has for it.

Labels follow [AGENTS.md](../../AGENTS.md). Source key: **[vice]** is the *VICE Design Specification*, document 099-0123-003, version 1.0, 17 April 1997 ([references/documents/specs/vice-design-specification-099-0123-003.pdf](../../references/documents/specs/vice-design-specification-099-0123-003.pdf), SHA-256 `c67e6ec6655b3682b3eaa2cb973236764d8c37ff03defa85eb3ebc6eaddaf804`); its printed page numbers equal the PDF page numbers. It describes the third chip revision (see `VICE_ID`). The copy in hand lacks the instruction-set appendix (printed pages 250 to 391 are absent), so the vector-unit and bitstream-processor instruction sets are unknown here, and the scalar encodings are absent ([Scalar unit](#scalar-unit) below); the register and DMA chapters are complete. **[report]** is the O2 Technical Report ([published-sources.md](../../references/documents/published-sources.md), source 1), **[spec]** the CRIME 1.5 specification.

## Block summary

- Established ([vice] PDF 15-21): the chip holds a media signal processor (MSP) with 6 KB of data RAM in three banks of 2 KB (A, B and C) and 4 KB of instruction RAM, a 32-bit scalar unit at 66 MHz issuing one instruction a clock, a 128-bit vector unit at 66 MHz with one multiply and one accumulate a clock, and dual-issue dispatch. A bitstream processor (BSP) has a 16-bit load-store core with multi-cycle extensions and programmable tables for JPEG, MPEG-1, MPEG-2 and H.261 decoding. Two DMA channels move data between system memory and any memory inside the chip. The MSP data and instruction sizes agree with [report] (published-sources.md source 1, which reads 6 KB and 4 KB), so that entry now has a second source.
- Established ([vice] PDF 19, 199): the whole chip runs on a 15 ns clock, 66 MHz, and the bus interface synchronises the roughly 100 MHz system bus to it.
- Established ([vice] PDF 19-20): a DMA mode splits 4:2:2 YCrCb in memory into separate luma and chroma blocks in data RAM (and the reverse), with optional chroma decimation to 4:2:0; a half-pixel mode (17 pixels in, 16 out) exists but its descriptor bits are marked "not implemented, do not use" ([vice] PDF 69).
- Established ([vice] PDF 18-20): the chip is a client of the CRIME processor-bus interface, using multiple outstanding reads that CRIME was extended to support, and arbitrates for the bus itself.
- Unknown: the vector and scalar instruction encodings, the BSP instruction set and table formats, and what the shipped converters upload. Routes tried: [vice] chapters 2 to 4 (the appendix is missing from the copy), [report], the Nintendo 64 signal processor guide in the library (a related design, not this chip), the converters' export lists. Next: disassemble `libvice.so` and the plug-ins for the code images they load.

## Address map and translation

- Established ([vice] PDF 22-24, table 2): system addresses `0x17000000` to `0x1700ffff` hold the chip: data RAM banks A, B and C at `+0x8000`, `+0x8800` and `+0x9000` (2 KB each), the bitstream processor's input and output buffers in `+0x7000` to `+0x7fff` (output at `+0x7000`, input at `+0x7800`), kernel-restricted registers at `+0xe000`, the translation buffer at `+0xf000`, and the ordinary registers in the low page. An access to an unimplemented part of a range reads zeros rather than faulting.
- Established ([vice] PDF 22-23): two address pins select one of four 1 MB blocks at `0x17000000`, `0x17100000`, `0x17200000` and `0x17300000`, matched against bus address bits 21:20 so that several chips could share the bus. The specification says more than one chip was never tested, even in simulation. The CRIME window of `0x17000000` for 16 MiB ([spec], [devices/crime/CRIME.h](../crime/CRIME.h)) agrees with the first block.
- Established ([vice] PDF 24-25, table 2): the instruction RAMs sit in the chip's window too. The MSP instruction RAM is 4 KB at `+0x2000` and the BSP instruction RAM is 1K by 16 bits (2 KB) at `+0x4000`. Each is loaded by the host and the DMA engine, and the owning processor can only fetch from it. The unimplemented tails and the reserved MSP expansion at `+0x3000` read zeros from the host.
- Established ([vice] PDF 24 and the block diagram): the bitstream processor's table memory is 1280 entries of 22 bits at `+0x5000` (the map gives 8 KB for the window). The 32-bit presentation of each entry is inferred from the span the map gives.
- Established ([vice] PDF 133): the specification says only big-endian mode is supported.
- Established ([vice] PDF 25, 33-35): the chip's own processors can address only its internal memories; system memory is reachable only by the DMA engines, through a 64-entry buffer that maps a 4 MB virtual space onto 64 KB physical pages, so one chip can touch at most 4 MB of memory at a time. Writing the buffer from the DMA engine needs a permission bit controlled by the host, and any address beyond the 4 MB range halts DMA and raises an interrupt.
- Established ([vice] PDF 35-36): two address spaces select how a DMA address is decomposed. The linear space (`0x00800000` to `0x00bfffff` in the chip's view) takes the buffer index from bits 21:16 and 16 bits of offset. The tile space (`0x10800000` to `0x10bfffff`, selected by bit 28) arranges the 4 MB as a 4096 by 1024 byte rectangle of 512 by 128 byte tiles, takes the index from bits 21:19 and 11:9, and hides page crossings so processors see raster order. The 512 by 128 byte tile equals the 64 KB frame-buffer tile of [spec] and [linux] `gbefb.c`; that is independent support for the size, which the rendering chapters already use.
- Inferred (arithmetic from the published geometry, [vice] PDF 35-36): for a DMA address `a` in the linear space, the buffer index is `(a >> 16) & 63` and the offset `a & 65535`. In the tile space the index is `(((a >> 19) & 7) << 3) | ((a >> 9) & 7)` and the offset `(((a >> 12) & 127) << 9) | (a & 511)`. The physical address is the entry's page number shifted left 16 places, OR'd with the offset. These follow from the 4096 by 1024 byte rectangle of 512 by 128 byte tiles; the specification gives the geometry, not these bit expressions.
- Established ([vice] PDF 38): a buffer entry is 32 bits, written whole: bit 0 valid, bit 1 writable (permits DMA writes to the page), bits 31:16 the 64 KB physical page number. The operating system's 4 KB page number of the first 4 KB of the range, shifted right by four, forms those upper bits. A missing entry gives the MSP a miss exception and halts the DMA engine ([vice] PDF 37, 65). This matches the user library's routines that set and update the VICE translation buffer (`vice_settlb`, `vice_updatetlb`, [binaries.md](../../evidence/binaries.md)); the match is by name and role, inferred.

## Registers

All registers sit on doubleword boundaries whatever their width; unused bits read zero ([vice] PDF 39, 44). Offsets are from the chip window. The `MSP` column of the register map ([vice] PDF 40-41) gives the coprocessor register the signal processor uses for the same register; the MSP cannot see the host-only ones.

### Chip

The registers in this and the next two sections, with the shared interrupt cause, mailbox and DMA control and status layouts, are recorded in [generated/c/vice.h](../../generated/c/vice.h). The descriptor registers are not. The memory regions (bitstream buffers, data RAM banks) and the translation buffer's first entry and entry format are listed in the same header; the access widths of the regions are inferred.

- `VICE_ID` at `+0x8`: established ([vice] PDF 40, 44). The read-only revision register; its low nibble numbers the chip revision from one to three, and the register map gives it a reset value of `0xe1`. A family tag in the high nibble is inferred.
- `VICE_CFG` at `+0xe000`: established ([vice] PDF 40, 44). Bit 0 asks the chip to check the data-error flag on bus data it receives; bit 1 lets the MSP bypass the translation buffer when the DMA control register also asks for it. Both reset to zero; the bypass bit is the host's safety switch.
- `VICE_INT` at `+0x160`: established ([vice] PDF 46, 41). The read-only cause register, nine active-high bits set by hardware and cleared through the reset register; each DMA channel has a completion and an error bit, and the rest are software, exception and bad-data causes.
- `VICE_INT_RESET` at `+0xe008`: established ([vice] PDF 45). Write-only; a one clears the matching cause and a zero does nothing.
- `VICE_INT_EN` at `+0xe010`: established ([vice] PDF 47). A read and write mask with the same bit order; masking only stops the pin, since `VICE_INT` shows the cause regardless.
- `MSP_SW_INT` at `+0x1b8`: established ([vice] PDF 47). Write-only; any write sets the MSP software interrupt cause even when it is masked.
- `BSP_SW_INT` at `+0x80`: established ([vice] PDF 47). The same for the BSP, set by any write.

### Media signal processor

- `MSP_CTL_STAT` at `+0x40`: established ([vice] PDF 49). Bit 0 starts the MSP when written one and halts it when written zero, and reads as running or halted; bit 1 releases the MSP from reset. Writing zero stops and resets it. The usual start is reset release, program counter load, then go.
- `MSP_PC` at `+0x50`: established ([vice] PDF 50). Bits 15:2 hold the word address. Writing sets the fetch counter but reading returns the decode counter, so a read straight after a write differs.
- `MSP_BadAddr` at `+0x58`: established ([vice] PDF 50). A read-only 32 bits, the load or store address that caused an address-error exception.
- `MSP_WatchPoint` at `+0x60`: established ([vice] PDF 50). A doubleword-granular physical address in bits 31:3; a load or store to it raises the watchpoint exception.
- `MSP_EPC` at `+0x68`: established ([vice] PDF 51). The read-only program counter of the instruction that caused the exception, bits 15:2.
- `MSP_CAUSE` at `+0x70`: established ([vice] PDF 51). The read-only exception code in bits 6:2 (address errors, break, watchpoint, reserved instruction in either unit, contention, instruction fetch) with a branch-delay flag in bit 31.
- `MSP_ExcpFlag` at `+0x48`: established ([vice] PDF 52). One sticky bit per exception code, cleared by software; all bits must be cleared before new exceptions are detected, and it shows exceptions that coincide when the cause register can hold only the highest priority.
- `MSP_D_RAM` at `+0x100`: established ([vice] PDF 48). Three enable bits, one per data RAM bank, say which banks the scalar unit may touch. A load or store to a disabled bank is ignored and reads unknown data. Enabling all three is safe but stalls DMA on every scalar access.
- `VICEMSP_COUNT` at `+0x108`: established ([vice] PDF 53). A writable 32-bit free-running clock counter; at 66 MHz it wraps in about 65 seconds (71.6 s at 60 MHz).

### Scalar unit

The scalar unit is a pipelined processor for a subset of MIPS I. The specification lists its mnemonics ([vice] PDF 122-124) but not their instruction formats, so the scalar encodings are unknown here.

- Established ([vice] PDF 122-124): the scalar unit implements the ALU, shift, load and store, branch, jump and coprocessor move families, and the vector unit's loads and stores are overloaded onto the coprocessor 2 opcodes ([vice] PDF 123-124). It does not implement BCzT, BCzF, SYSCALL, MULT or DIV; multiplies belong to the vector unit ([vice] PDF 124).
- Established ([vice] PDF 120, 131): 32 registers of 32 bits, two read ports and one write port. The shifter shifts by 0 to 31 bits in the ALU cycle, taking the amount from a 5-bit instruction field or from the low five bits of `rs`.
- Established ([vice] PDF 125, 130-131): five stages, IF, RD, EX, LS and WB. Two multiplexers in front of the ALU forward results that are still in the pipeline.
- Established ([vice] PDF 117): an issue group holds at most one scalar and one vector instruction, in either order. Coprocessor moves and vector loads and stores count as scalar instructions for grouping. A branch delay slot always issues alone, and a branch may be the second half of a group whose first half is a vector computation.
- Established ([vice] PDF 125-126): the branch target is computed in RD and the condition in EX. A taken branch or jump costs no penalty. An untaken branch costs one cycle to refetch the in-line stream. The delay slot executes on both outcomes ([vice] PDF 126, figures 37 and 38).
- Established ([vice] PDF 131): the programmer must place an instruction with no dependency on the two preceding instructions in the delay slot, or a NOP. The specification states this as a rule on the programmer and gives no interlock for the slot; that the hardware does not stall for it is inferred.
- Established ([vice] PDF 127): a load, MFCz or CFCz result is available two cycles later, and the hardware interlocks a dependent instruction. The check compares the destination with the RS field of every valid scalar instruction and with the RT field of all of them except LWC2, SWC2 and immediate instructions. The specification says this may cause false stalls, and Table 70 gives the field positions for each instruction.
- Established ([vice] PDF 127, table 70): in coprocessor moves the RS field selects the transfer: 0 for MFC, 2 for CFC, 4 for MTC and 6 for CTC.
- Established ([vice] PDF 117): the instruction PC is 32 bits wide, but bits 31:16 and 1:0 are grounded. A `jr` to an unaligned address, or to one with high bits outside instruction RAM, is not detected. A branch offset that carries past instruction RAM is not detected either.
- Established ([vice] PDF 29): in this implementation the PC is 14 bits wide and the fetch range check uses bits 15:3. An address outside instruction RAM, or beyond the implemented range, raises AdEI (code 7). BadAddr is not updated, and EPC holds the instruction's PC.
- Established ([vice] PDF 28): an undefined major opcode or SPECIAL function raises SuRI (code 4), with EPC at the instruction. The specification says an encoding outside its exact detection definition falls to the nearest synthesized opcode, which is nondeterministic.
- Established ([vice] PDF 27): a load or store raises AdEL or AdES when it touches instruction RAM, lies outside the valid MSP address space or the implemented physical range, or is misaligned. The loaded value and the stored data are undefined.
- Established ([vice] PDF 28): BREAK raises BP (code 2), with EPC at the BREAK. It should not sit in a delay slot. It is precise when the next instruction is not a vector computation, or when BREAK is the second instruction of a group.
- Established ([vice] PDF 28): the watchpoint compares addresses with the low three bits ignored. The load or store that matches still completes. Writing zero to the watchpoint register disables it.
- Established ([vice] PDF 28): a scalar load or store to a data bank that MSP_D_RAM has not enabled raises Con (code 6).
- Established ([vice] PDF 27, 29, 31, 237): exceptions are imprecise. On detection the MSP issues nothing new, finishes the instructions already in its pipeline and halts. Its PC is then indeterminate and the host must write it before a restart. Load, store and contention faults are detected in write-back and the others in decode, so a BREAK right after a load fault reports BP in the cause, and both flags are set.
- Established ([vice] PDF 29): when several exceptions arise in one cycle, the priority is instruction fetch, BREAK, scalar reserved instruction, vector reserved instruction, contention, load address error, store address error, watchpoint. The cause and EPC record the winner. EPC, Cause and BadAddr are not updated again until every flag bit is clear.
- Established ([vice] PDF 22): the MSP does not respond to interrupts. It only halts on an exception and can be halted and restarted through MSP_CTL_STAT.
- Established ([vice] PDF 119): the MSP cannot be stalled. A bank it may access is served at once, and the DMA engine and the bitstream processor are arbitrated around it. Enabling all three banks is safe but slows the other units. The enable bits are a hint to the arbiter ([vice] PDF 48).
- Established ([vice] PDF 129, 132-133): a data RAM access reads 128 bits, and the crossbar rotates and formats them. LB and LH sign-extend and LBU and LHU zero-extend. Only big-endian byte order is supported. Each bank is 2 KB and writes are byte-granular.
- Established ([vice] PDF 26): a register-initiated reset holds for at least 16 clocks before it is released. The PLL of the whole chip needs 100 ms to stabilise.

### Bitstream processor and mailboxes

- `BSP_CTL_STAT` at `+0x110`: established ([vice] PDF 54, figure 47 on PDF 178-179). Bits 15 to 12 are the arithmetic flags (negative, zero, carry, overflow), zero after reset and changed only by arithmetic. Bits 11 to 9 are three software-set condition bits (EXT0 to EXT2) that branches can test. Bit 8 says the write buffer is empty, bits 7 and 6 mask the FIFO-empty-too-long and code-not-found interrupts (both reset masked), bits 5 and 4 reset the output and input bit counters on a one-to-zero change, bit 3 is an auto-increment control, bit 2 clears the bitstream buffer's valid-bit count on a one-to-zero change, bit 1 picks the zig-zag (0) or the alternate (1) coefficient scan, and bit 0 says the encode pipeline is empty. The bit positions below bit 6 are read from the figure; the text names the bits but gives no numbers. Bit 3's exact effect is not described.
- `BSP_WatchPoint` at `+0x118`: established ([vice] PDF 54). A halfword address in bits 15:1; bit 0 is ignored so byte and halfword accesses both match.
- `BSP_IN_COUNT` at `+0x120`: established ([vice] PDF 55). A 24-bit count of 32-bit transfers from the input FIFO into the BSP, which with the F valid-bits pointer lets the host compute bits consumed for rate control in decoding.
- `BSP_OUT_COUNT` at `+0x128`: established ([vice] PDF 55). A 24-bit count of 16-bit transfers into the output write buffer, for the host's buffer control in encoding.
- `BSP_PC` at `+0x140`: established ([vice] PDF 59). The 16-bit BSP program counter, reset to zero so an uninitialised BSP starts at instruction address zero.
- `BSP_EPC` at `+0x148`: established ([vice] PDF 59). The read-only 16-bit address of the instruction that raised an exception, captured when the halt bit is set.
- `BSP_HALT_RESET` at `+0x150`: established ([vice] PDF 60). Bit 1 releases the BSP from reset and the go bit starts it; clearing stops and resets it. A halt request completes in-flight instructions first and can wait forever on an unresolved stall.
- `BSP_CAUSE` at `+0x158`: established ([vice] PDF 61). The read-only flags for the load and store address errors, break, reserved instruction, instruction address, bitstream error and write-buffer address error; the watchpoint flag exists but is "not implemented". A bitstream error does not stop the BSP: it jumps to instruction address `0xc0`.
- `BSP_FIFO_CTL_STAT` at `+0x168`: established ([vice] PDF 62). Reports the 16-entry input FIFO empty (reset 1) and full flags, resets that FIFO, and carries two software signal bits wired straight to chip output pins.
- `BSP_AVALID_BITS` at `+0x170`: established ([vice] PDF 63). A six-bit valid-bit pointer for the decode FIFO, reset to zero.
- `BSP_FVALID_BITS` at `+0x178`: established ([vice] PDF 63). The same six-bit pointer for the encode FIFO, used with the counters above.
- `BSP_RPAGE` at `+0x78`: established as a map entry, 16 bits read and write ([vice] PDF 40); no register section describes it. The architecture chapter (PDF 178) names an RPage register in the bitstream processor's alternate set as the base for its loads and stores. That the host sees this same register is inferred. Next: the converters' use of the register.
- `BSP_IN_BOX` at `+0x1f0`: established ([vice] PDF 56). A 15-bit message from the MSP to the BSP; bit 15 is set by any write and cleared by a read, so the sender can see whether the message was read.
- `BSP_OUT_BOX` at `+0x1f8`: established ([vice] PDF 57). The reverse mailbox with the same self-clearing bit 15, written by the BSP and read by the MSP.
- `HST_BSP_IN_BOX` at `+0x28`: established ([vice] PDF 58). A host-only shadow that reads the input mailbox without clearing its flag.
- `HST_BSP_OUT_BOX` at `+0x30`: established ([vice] PDF 58). The shadow of the output mailbox, likewise without side effects.

### DMA channels

- `DMA_CTL_CH1` at `+0x180`: established ([vice] PDF 64). Go (cleared by hardware when done), interrupt enable, stop, reset, a four-bit one-hot choice of first descriptor set, translation-buffer bypass and flush bits. Writing zero to go does not stop a transfer; stop does.
- `DMA_STAT_CH1` at `+0x188`: established ([vice] PDF 65). The read-only done, error, active and direction flags, the descriptor set in use and a four-bit state code: idle, halted by stop or by the descriptor, computing, waiting on CRIME for addresses or data, moving data, halted by a buffer miss or by a write to a read-only page, fetching descriptors.
- `DMA_DATA_CH1` at `+0x190`: established ([vice] PDF 66). A 16-bit pattern repeated four times to a 64-bit word for the fill mode. Fill can target only chip memory, not system memory; system memory is filled by filling data RAM and then writing it out.
- `DMA_MEM_PT_CH1` at `+0x198`: established ([vice] PDF 66). A read-only diagnostic copy of the last physical system address the engine computed, four-byte aligned.
- `DMA_VICE_PT_CH1` at `+0x1a0`: established ([vice] PDF 66). A read-only diagnostic copy of the last chip-internal address.
- `DMA_COUNT_CH1` at `+0x1a8`: established ([vice] PDF 67). The read-only bytes left in the current descriptor.
- `DMA_CTL_CH2` at `+0x1c0`: established ([vice] PDF 64). The second channel's control register, the same layout as channel 1.
- `DMA_STAT_CH2` at `+0x1c8`: established ([vice] PDF 65). The second channel's status, the same layout as channel 1.
- `DMA_DATA_CH2` at `+0x1d0`: established ([vice] PDF 66). The fill pattern that the second channel replicates into each 64-bit word.
- `DMA_MEM_PT_CH2` at `+0x1d8`: established ([vice] PDF 66). The second channel's system-address diagnostic.
- `DMA_VICE_PT_CH2` at `+0x1e0`: established ([vice] PDF 66). The second channel's internal-address diagnostic.
- `DMA_COUNT_CH2` at `+0x1e8`: established ([vice] PDF 67). Bytes still to move in the descriptor the second channel is working on.

Each channel has four descriptor sets of eight 16-bit registers, stored at a stride of `0x40` from `+0x1000` for channel 1 and `+0x1100` for channel 2 ([vice] PDF 42-43, tables 6 and 7). The sets run in order without host help, and any descriptor can halt the channel after it completes ([vice] PDF 68). The control word of every set uses the `DMA_DESC_CTL` layout ([vice] PDF 68-70, table 43): bits 1:0 and 9:8 are the half-pel flags (not implemented), bit 2 chroma only, bit 3 the half-pel enable, bits 6:4 the location (not implemented; the addresses select the target), bit 7 interleave (block mode is required), bits 11:10 the Y/C mode, bit 12 the fill source, bit 13 the direction (1 reads system memory into the chip, 0 writes out), bit 14 skip and bit 15 halt. The printed address table repeats the selector label `$11` for two channel 2 registers in set 2 ([vice] PDF 43); the address column follows the stride, so the labels are taken as a typo.

- `DMA_CTL_CH1_D1` at `+0x1000`: established ([vice] PDF 68-70). The descriptor's mode word: read or write, location inside the chip, block or interleave, luma half-pixel flags (not implemented), the Y/C split choices, fill, skip and halt. Block mode is the only working interleave setting.
- `DMA_SMEM_HI_CH1_D1` at `+0x1008`: established ([vice] PDF 71). Upper 16 bits of the system address, virtual through the buffer or physical when bypassed; bit 28 chooses the tile space.
- `DMA_SMEM_LO_CH1_D1` at `+0x1010`: established ([vice] PDF 71). Lower 16 bits of that address; it must be 16-byte aligned in Y/C split modes.
- `DMA_WIDTH_CH1_D1` at `+0x1018`: established ([vice] PDF 71). Bytes in one memory strip, a multiple of 16 in the split modes.
- `DMA_STRIDE_CH1_D1` at `+0x1020`: established ([vice] PDF 71-72). Bytes from the start of one strip to the next; for a 720 pixel 4:2:2 image at two bytes a pixel it is 1440.
- `DMA_LINES_CH1_D1` at `+0x1028`: established ([vice] PDF 72). Number of strips to transfer.
- `DMA_VMEM_Y_CH1_D1` at `+0x1030`: established ([vice] PDF 72). Chip-internal start address of the luma (or only) block, 8-byte granular.
- `DMA_VMEM_C_CH1_D1` at `+0x1038`: established ([vice] PDF 72). Chip-internal start address of the chroma block; ignored in plain block mode.
- `DMA_CTL_CH2_D1` at `+0x1100`: established ([vice] PDF 42-43). Channel 2's first descriptor mode word, the same fields as channel 1's.
- `DMA_SMEM_HI_CH2_D1` at `+0x1108`: established ([vice] PDF 43). Channel 2's upper system address half.
- `DMA_SMEM_LO_CH2_D1` at `+0x1110`: established ([vice] PDF 43). Channel 2's lower system address half.
- `DMA_WIDTH_CH2_D1` at `+0x1118`: established ([vice] PDF 43). Channel 2's strip width in bytes.
- `DMA_STRIDE_CH2_D1` at `+0x1120`: established ([vice] PDF 43). Channel 2's strip stride in bytes.
- `DMA_LINES_CH2_D1` at `+0x1128`: established ([vice] PDF 43). Channel 2's strip count.
- `DMA_VMEM_Y_CH2_D1` at `+0x1130`: established ([vice] PDF 43). Channel 2's internal luma address.
- `DMA_VMEM_C_CH2_D1` at `+0x1138`: established ([vice] PDF 43). Channel 2's internal chroma address.

DMA restrictions ([vice] PDF 33): fill does not work in Y/C split mode; split, luma-only and chroma-only modes need quadword width and start; the 4:2:2 to 4:2:0 split overwrites the chroma of the first line with the second, which is wrong for transfers that start on an odd line and was to be corrected in the next chip revision. Established.

## Microcode shipped with the IRIX installation media

Not in `root/`; read from the 6.5 base media directories `var/arch/vicedx/` and `var/arch/vicetre/` (file names and sizes only, content not read). `usr/lib/internal/libvice.so` names three directories, `/var/arch/vice/`, `/var/arch/vicedx/` and `/var/arch/vicetre/`, and the media have the last two (established).

- Established: both sets hold the same 32 file names: JPEG (`cjpeg`, `cjpeg_luma`, `cjfif`, `djpeg`, `dfjpeg`, `djfif`, with `cjpeg-mcoef.bin`, `djpeg-mcoef.bin`, `cjpeg.btbl`, `djpeg.btbl`), DV (`dvcntsc`, `dvcpal`, `dvcpal411`, `dvcpal420`, `dvencodentsc`, `dvencodepal411`, `dvencodepal420`, `dvcVLC.bin`), MPEG decode (`mpeg1dec`, `mpeg2dec`, `mpeg2dec_fld`, `m1tabs.btbl`, `m2tabs.btbl`) and a resize program (`rs.mex`). Compared byte for byte, every `.bex`, `.bin` and `.btbl` file and the six DV `.mex` files are identical in the two sets; ten `.mex` files differ in size, DX larger than TRE (for example `mpeg1dec.mex` 4048 and 3492 bytes, `djpeg.mex` 3424 and 3056, `rs.mex` 3452 and 2976). So the two chip variants differ in the programs of one processor, for the JPEG, MPEG and resize work, and not for DV (inferred: `.mex` as the media signal processor's programs and `.bex` as the bitstream processor's, from the extensions; content not read).
- Established (read 2026-11, [routines/oq-vicempeg-send.md](../../evidence/routines/oq-vicempeg-send.md)): the shipped MPEG converter plug-in `vicempeg.so` has an MPEG-2 path. It registers the format names "MPEG-1 Video" and "MPEG-2 Video" (strings at `.rodata` `0x4040b0` and `0x4040c0` of the N32 build), and its `Send` routine (0x401788) loads the MPEG-2 programs `mpeg2dec.mex`, `mpeg2dec.bex` and `m2tabs.btbl`, or `mpeg2dec_fld.mex`, `mpeg2dec_fld.bex` and `m2tabs.btbl`, when the buffer's compression parameter is "MPEG-2 Video" (compare at 0x401bc0), and the MPEG-1 set otherwise. The premise that the shipped software has no MPEG-2 entry point is contradicted at the loader level: both an MSP program and a bitstream program for MPEG-2 decode are named and loaded.
- Inferred: the two MPEG-2 variants are frame and field decoding. The choice is a test of one word of the buffer's user-data record against 3 (0x401be0): 3 picks the plain program and anything else the `_fld` program, and 3 is the code ISO/IEC 13818-2 gives a frame picture (1 and 2 are the two fields). The word's producer was not read.
- Unknown: what is inside the MPEG-2 programs and where their entry points are. The program files are on the installation media only, whose contents this repository holds by name and size ([above](#microcode-shipped-with-the-irix-installation-media)); the instruction sets are the part of [vice] missing from its copy. Route: read the three programs from the 6.5 base media once a copy is held, against the instruction encodings recovered from `libvice.so` and the converters.
- Established (searched 2026-11): no DVD-specific name appears in the 260 files of `root/` (the only case-insensitive match for the three letters is inside the unrelated string `vs2LoadVdrc` in `gfxinit` and `setmon`), nor among the 32 microcode file names above. The converters present are `vicedv.so`, `vicejpeg.so`, `vicempeg.so` and `vicers.so`; `vicedv.so` and the `dvc` and `dvencode` programs carry NTSC and PAL in their names, which fits DV camcorder video (inferred from the names). No shipped dependency on a DVD decode path exists in the files held. The claim that DVD decode was planned and dropped is not testable from them; it stays an unverified lead ([published-sources.md](../../references/documents/published-sources.md), the Hacker News entry).
- Established: `sbin/hinv` of the 6.5.30 media prints `Vice: %s` and `Vice: %x` and `Video: MVP unit %d version %d.%d`; the kernel adds the VICE inventory entry only when bit 31 of the CRIME interrupt status is set ([functions.md](../../software/kernel/functions.md), `add_vice`).

## Reported behaviour from software users

- Established (published output, `hinv` dumps from O2 hosts): the inventory line is `Vice: TRE` (193 dumps) or `Vice: DX` (72), and the video line `Video: MVP unit 0 version 1.4` (187 dumps), `1.2` (65) or `1.3` (7). Every pairing of the two variants with the three versions occurs (TRE with 1.4 in 150 dumps, with 1.2 in 37, with 1.3 in 2; DX with 1.4 in 34, with 1.2 in 25, with 1.3 in 5). DX goes with the early CPU modules: R5000 at 180 MHz or less (60 dumps) and R10000 at 175 MHz or less (11, chip revision 2.5 in 10 of them); no DX dump has an R12000 (38 TRE dumps) or a faster clock, while TRE is on R5000 up to 300 MHz, R10000 and R12000. The graphics revision letters do not move with the Vice variant: all 56 `gfxinfo` dumps for the CRM board print CRM revision C and GBE revision B.
- Inferred (secondhand: [a developer's 2002 post on imaging for O2](../../references/documents/reports/o2-imaging-techniques-usenet-2002.txt) and [a list from an SGI engineer reproduced on a hobbyist site](../../references/documents/reports/sgidepot-melting-the-ice.html)): the imaging extensions run on the chip only when every coefficient of an operation is either an integer of magnitude above one or a real in -1.0 to 1.0, never mixed; otherwise the CPU does it at a fraction of the speed. Capture is accelerated only for PAL and NTSC frame sizes. These describe what the IRIX driver does on top of the hardware, not the hardware itself.

## IRIX identity probe

The IRIX kernel probes for the chip once, at boot, and adds an inventory entry when it answers. The register sequence is in [functions.md](../../software/kernel/functions.md) under `add_vice`. The probe reads the 32-bit ID word at `+0xc`, the low half of the `VICE_ID` doubleword at `+0x8` (`add_vice`, `kernel.o` offset `0x8168`, a `lw` from `+0xc` passed as the last argument of `add_to_inventory`).

- Established ([vice] PDF 44, table 8, and the published `hinv` dumps above): `hinv` prints `Vice: DX` for revision 2 and `Vice: TRE` for revision 3.
- Unknown: the names `hinv` prints for ID words `0xe1` and `0xe4`, the form it prints for any other word, and whether it compares the whole 32-bit word. These came from a reading of `sbin/hinv` that cannot be repeated here, because `sbin/hinv` is not in `root/`. Route: read `sbin/hinv` from the 6.5.30 media and check the compare and the name table.
- Inferred (`libvice.so` of the same media, read from its disassembly): the library picks the microcode directory from the same word, obtained through a driver ioctl whose code was not read. It tests for `0xe1` (directory `vice`) and `0xe2` (`vicedx`) and takes `vicetre` for every other word (`vice_file`, N32 `libvice.so`, compares against 225 at `0xd0024b8` and 226 at `0xd0024a8`).
- Established (kernel `add_vice`): the probe writes `4` to the enable word at `+0xe014`, the low half of the slot at `+0xe010`, and does not restore it, so cause 2 stays enabled after boot. Other writers of that slot were not checked.
- Unknown: the value of the upper word of the ID doubleword, and whether any later consumer reads the ID again. The library reads it once through the driver when it chooses the directory.

## Conflicts and open points

- Conflict between published tables: `DMA_VICE_PT_CH1` and `CH2` are 16 bits in the register map ([vice] PDF 40, rows `0x1a0` and `0x1e0`), but their register format table gives 32 bits, the C pointer in bits 31:16 and the Y pointer in bits 15:0 ([vice] PDF 66, table 41). The defs keep 16 bits from the map. Unresolved.
- Conflict: `VICEMSP_COUNT` is read-only in the register map (PDF 40) and read/write in its register format table (PDF 53, table 22). The defs keep read/write from the table.
- Conflict: `msp_i_ram`'s access width. The DMA location table lists MSP instruction RAM at 16 bits (PDF 69), while the defs use 32 bits inferred from the scalar instruction size. Unresolved.
- Open: the register that holds the host permission for DMA writes into the translation buffer is not identified in the text read here ([vice] PDF 25). `VICE_CFG` bit 1 is the MSP bypass permission, not this one.
- Open: the 8-byte stride of the 64 translation entries is inferred from the register slot pattern. The map gives only a 4 KB window for them ([vice] PDF 24).

- Conflict inside the specification, not only against the report: the design text gives the chip one 15 ns, 66 MHz clock ([vice] PDF 199; the input pin `VClock` is described as 66 MHz), while the AC characteristics table gives the clock period rate as 60 MHz maximum, a 17 ns minimum cycle (table 80, PDF 235). [report] rates the bitstream processor at 60 MHz, which agrees with that table, and no source gives the bitstream processor a separate clock. Established: both numbers are in the specification and the chip has one clock input. Inferred: the report's figure is the characterised maximum of that clock, not a second clock. Unknown: the frequency the shipped board drives (the specification covers revision 3; no shipped software reads or depends on it). Test on hardware: read the free-running counter at `+0x108` twice, a few seconds apart, against a MACE timer; 66 MHz wraps the 32-bit counter in 65 s and 60 MHz in 71.6 s. Test that would settle it: the counter read described above, taken once on hardware.
- Agreement: both give two DMA channels with host, MSP and BSP programmability; the 64 KB translation granule matches [spec]'s 64 KB tile.
- Conflict: the exception flag register's note says every flag bit must clear before exceptions are detected ([vice] PDF 52), while the exception section says later exceptions set their flags and only the EPC, Cause and BadAddr updates wait for a clear ([vice] PDF 29). Unresolved; the published text does not say what a second exception in a drain does to the flags.
- Conflict: the descriptor path for channel 2. The common-bus section says the scalar unit reaches channel 2 descriptors with CTC1 and CFC1 ([vice] PDF 118), while the address map gives the whole `+0x1000` to `+0x1fff` descriptor range to MTC3 and CTC3 ([vice] PDF 24). Unresolved.
- Conflict: the scalar instruction set is a subset of MIPS I in one place ([vice] PDF 120) and of "MIPS R300" in another ([vice] PDF 122). The mnemonic list is the same either way.
- Open: halfword alignment. The address-error section requires halfwords to sit on a word boundary ([vice] PDF 27), which differs from ordinary MIPS two-byte alignment. The text does not say which was built.
- Conflict: the DMA location table gives the BSP instruction RAM a width of 64 bits and the BSP table RAM 32 bits ([vice] PDF 69, table 43), while the register map gives the BSP instruction RAM as 1K by 16 bits ([vice] PDF 24). The defs keep 16 bits from the map. The 32-bit table RAM agrees with the presentation inferred above. Unresolved.
- Open: the full-chip reset length is printed as "16 clocks?" with a question mark ([vice] PDF 26). The register-initiated reset of at least 16 clocks is stated without one.
- Open: a failing scalar load or store has undefined data and an undefined memory effect ([vice] PDF 27). The spec does not say what the host should expect to read back.
- Open: DMA may write MSP instruction RAM while the MSP runs ([vice] PDF 30), but the text does not say whether an already fetched word sees that write.
