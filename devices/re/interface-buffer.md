# Interface buffer: the register at +0x4008, the reset at +0x408, the status word and a full buffer

What shipped IRIX software expects from the rendering engine's host interface buffer: what its two odd registers do, how it reads the status word, and what the CPU is meant to see as the buffer fills. Register layout is in [registers.md](registers.md) (`ib_data`, `ib_addr`, `ib_ctl`, `ib_reset`, `status`, `ib_discard`); the save and restore code is in [../../software/kernel/context.md](../../software/kernel/context.md), the wait messages in [../../software/kernel/diagnostic-messages.md](../../software/kernel/diagnostic-messages.md), the initialisation order in [../../software/kernel/reset.md](../../software/kernel/reset.md).

Labels: **established**, **inferred**, **unknown** (routes tried listed). Tags: `[binary]` a shipped IRIX 6.5.30 O2 object read here (`crime.a` members, `kernel.o`, `crm.so`, `libGLcore.so`, `ip32prom.image`); `[public]` the CRIME 1.5 specification. Offsets of kernel routines are `.text` offsets in the named archive member.

## Answers

| Question | Answer | Label |
|---|---|---|
| What is `+0x4008` | A write-only word the kernel stores 0 to after bulk register and tile-table loads and after saving a client's queued writes. It must not lose earlier writes. The model-safe behaviour is to accept the write and change nothing observable | established (18 sites, none depends on any other effect), inferred (hardware mechanism) |
| Is it "discard" | No evidence supports dropping queued writes, and 12 sites contradict it | established (the contradiction), unknown (the mechanism) |
| What `+0x408` clears | Not shown. Every writer stores 0, waits 10 microseconds and rewrites `+0x400`; the TLBs are reloaded afterwards only on the initialisation path | inferred |
| Idle word | Status bit 28 reads 1 when the engine is idle; the kernel also requires the level field, bits 24:18, to be 0; libGLcore requires only bit 28 | established |
| Level field | Bits 24:18, number of queued writes, 7 bits; the kernel treats 65 or more as an overflow | established |
| Full buffer, CPU view | Above the stall level the CPU's stores stall; above the interrupt level input 26 asserts and the kernel sleeps the writer; shipped software never lets the 64-entry ring fill | established (software), `[public]` (hardware text) |

## The ring and the status word

- `[binary]` The kernel treats the ring as 64 entries (`mte_fifo_wait` tests `64 - level >= n`; `crmSavePP` wraps its index at 64; `crmFindPP` wraps at 63 and 0). `[public]` The specification's table says 128 (Table 7-1, PDF 163-164); the data and address halves are 512 bytes apart, which fits 64 doublewords. Established for the software's view.
- `[binary]` The status word `+0x4000` is read with 32-bit loads in every shipped use. Fields as software uses them: `level` bits 24:18, `rd_ptr` 17:12 (not read by shipped software), `wr_ptr` 11:6, `start` 5:0. `crmSavePP` (`crime.o` +0x2ff8) computes `(bits 11:6) - (bits 5:0)`, adds 64 if negative, and saves that many entries starting at index `bits 5:0`. Established. The entries are read from the ring RAM: the address half with a 64-bit load at `+0x200 + 8 i` (`crmSavePP`) or two 32-bit loads (`crmFindPP`), the data half as two 32-bit loads at `+8 i` and `+8 i + 4` (`crmSavePP`). A model that serves both reads must give both widths the same bytes. Established.
- `[binary]` Reads of `+0x400` exist in shipped code: `crimeFifoFullHandler` loads it into the argument of its `Cfifo Overflow` message (`crime.o` +0x344), and `ip32prom.image` loads it at image offsets `0x15894` (run-time `0x8100c594`, the timing choice) and `0x38c54` (`0x8102f954`, the routine that names the graphics record `SGI-CRM, Rev B` or `Rev C`). Both test only bit 0 of the result and nothing in the PROM stores to the offset: bit 0 clear gives revision B (flag byte 1) and set gives revision C (flag byte 2), and in the timing choice it picks one of two timing-table entries for each matched monitor-flag bit (the PROM page in the chips repository, section "Rendering-engine control word"). So the control word is readable on at least some paths although the specification lists it as write-only, and the PROM treats its bit 0 as a board-revision discriminator. Established that the loads exist and what they select; what bit 0 means in hardware is unknown (it is the lowest bit of the stall-cycle count field under the inferred layout below, and the kernel's first control word `0x0fefff0a` has it clear). Routes tried: the PROM routines read in full at the two sites, the kernel (reads it only in the overflow message), the specification (write-only). A model should return the last value written, and zero before any write, which gives the PROM revision B; the reset value is unknown: no shipped software or published source depends on it beyond these two tests.

## The register at +0x4008

- `[binary]` Every store to `+0x4008` in the held kernel is a 32-bit store of zero: 18 sites, listed with what precedes each. `crimeInitHW` (`crime_init.o`): four times, after each batch of eight frame-buffer TLB indices (preceded by `crmFifoWait` for room), after the linear TLB clear and after the texture TLB clear. `crmLoadTlbABC` (`crime_tiles.o`): twice, after loading the frame-buffer tables. `crmValidateDrawable`: twice, once after its table loads and once after `crmLoadTexTlb`. `crmLoadCidTlb`: once, after the clip-ID table ([clip-id.md](clip-id.md)). `crime_load_linear_tlb`: twice, after the linear table. `crimePixelDma` (`crime_dma.o`): once, after it rewrites ClipMode. `crimeValidateClip` (`crime.o`): once, after storing ClipMode, the screen masks and the window offsets and before replaying the client's saved writes. `crimePcxSwap`: twice, once before `crmIdleWait` and once after loading the incoming client's global and non-global registers from its shadow. `crmSavePP`: once, after it has copied the queued entries out. `crimeRestore`: once, after the linear tables are restored and before saved writes are replayed. `crimePrivate`: once, after `crmLoadTexTlb`. Established, each site read.
- `[binary]` In 12 of the 18 sites the stores just before it are tile-table or register loads the kernel needs in effect (`crmLoadTlbABC`, `crmValidateDrawable`, `crmLoadCidTlb`, `crime_load_linear_tlb`, `crimePixelDma`, `crimeValidateClip`, the second `crimePcxSwap` site, `crimeRestore`, `crimePrivate`). The four `crimeInitHW` sites follow table clears, which are moot only if the tables already reset to zero (unknown). The remaining two are in the save path (`crmSavePP` and the first `crimePcxSwap` site, which follows it). A write that dropped queued entries would remove the table loads and register restores that precede the twelve, so the kernel would not work. Established as a contradiction of the name `ib_discard` and of any reading in which the write discards writes already made.
- `[binary]` Writes also take effect without it: `mte_set_tlb` and `mte_copy` (`kernel.o`) load the linear tables and start copies with no store to `+0x4008` at all. Established (no store to the offset anywhere in `kernel.o`). So a register write needs neither this store nor any other to be applied, and the register is not a commit.
- `[binary]` Whatever the hardware does, the saved-entries bookkeeping explains where the kernel wants it. `crmSavePP` and `crmFindPP` treat the entries between the status `start` and `wr_ptr` fields as the client's not-yet-committed writes. Writing the register after a bulk load by the kernel itself, or right after the save, keeps the kernel's own writes from being counted as the next client's pending state, and in `crimePcxSwap` it precedes the wait for the level to reach zero. Inferred: the write moves the `start` field to the write pointer. This fits all 18 sites and is not shown by any one of them.
- `[public]` No public source read for this page names the register (the specification's address map has no entry at the offset; NetBSD was not re-read here). The user-mode libraries and the X module never write it ([opengl.md](../../software/opengl/opengl.md): libGLcore; `crm.so` has no store to the offset). Established as absences.
- Model-safe behaviour: accept the 32-bit write, apply earlier register writes as usual, and if the model keeps queue pointers set `start` to the write pointer. A model that applies every register write immediately can treat the write as having no effect. With that model the kernel's save path finds `start` equal to `wr_ptr` and level 0, calls `crmFindPP`, and `crmFindPP` reads ring entry 63; a zeroed ring entry reads as a write to an offset below `0x2000`, which it treats as a stop (global register write), so it returns "nothing to save". Established by tracing the routine against a zeroed ring.
- Unknown: the hardware's own effect on the queue pointers (whether `start` follows the write pointer, the read pointer, or nothing) and whether reading the register returns anything. No shipped software reads it. Routes tried: all 18 sites, the diagnostics in the earlier pass ([reset.md](../../software/kernel/reset.md)), the specification (silent), NetBSD, the PROM (no store with this offset: its engine accesses are the two loads of `+0x400` above). A hardware read is not needed to settle what a guest does.

## The reset at +0x408

- `[binary]` The writers of `+0x408` are `crimeInitHW`, `crimeError`, `crime_earlyinit` (`crime.o`, the second of the two `crime.o` sites the earlier pass listed) and the diagnostics ([reset.md](../../software/kernel/reset.md)), each a 32-bit store of 0. In `crimeInitHW`, `crimeError` and the diagnostics the write comes first, a delay of 10 microseconds follows (in `crimeError` the store sits in the delay slot of the `us_delay(10)` call), and the next engine write is the interface-buffer control word. In `crime_earlyinit` the store comes straight after the display back end is probed and stopped and is followed by the dual-channel probe, with no wait and no control-word write nearby; `crimeInitHW` runs later and programs the control word. Established.
- `[binary]` After `crimeInitHW` the TLBs are cleared and reloaded, so nothing shows what the reset does to them. After `crimeError` they are not touched: `crimeError` ends after rewriting `+0x400`, the callers (`crmSavePP`, `crimePcxSwap`, `crimeEmptyWaitTimeout`) return, and the next drawable validation reloads a frame-buffer table only when the drawable's incarnation counter differs from the loaded one, which nothing in `crimeError` changes ([memory.md](memory.md)). Inferred: a reset that cleared the TLBs would leave the screen unrenderable after a timeout, so the reset leaves TLB contents alone or the recovery is incomplete. Weak.
- Inferred, strengthened by one fact: the reset returns the control word to its unprogrammed value, since the three writers that wait reprogram it at once, and it empties the queue, since `crimeError` is the recovery from a queue that will not drain and it does nothing else to the queue. The new fact is `crimeError`'s ordering: reset, 10 microsecond wait, control word, no wait for idle. Unknown: whether the pixel pipeline, the transfer engine registers or the pointers in the status word change. Routes tried: all writers, their following writes, the specification, NetBSD, PROM (no store), MAME. Nothing shipped reads a register before writing it after the reset.
- Model-safe behaviour: on a write, empty the queue (pointers and level to 0, ring RAM to zero), set the control word to its reset value (unknown: the first shipped value is the all-thresholds-off word `0x0fefff0a`, which software writes immediately after), and leave the TLBs and pixel-pipeline registers as they are.

## The status idle word and the level field

- `[binary]` Readers of the status word and what each requires, all 32-bit loads:
  - `crmIdleWait` (`crime.o` +0x2dbc): polls every microsecond until bit 28 is set **and** bits 24:18 are 0, giving up after the passed number of microseconds and returning 1 (callers: `0xf4240` in `crimePcxSwap`, `0x1000` in `crimeInitHW`, `0x7a120` in `crimePixelDma`). Established.
  - `crmFifoWait`, `mte_fifo_wait`: level only. `mte_fifo_wait` needs `64 - level >= n`. `crmFifoWait` needs level at or below a target held in a kernel word minus `n`; the poll is capped at 100 microseconds before it sleeps on input 25 (messages: [diagnostic-messages.md](../../software/kernel/diagnostic-messages.md)). Established.
  - `crimeFifoFullHandler`: reads input 26's bit in the CRIME interrupt status (`0x14000010` bit 26) then the level field and loops up to 100 microseconds until the level is below the full threshold in the kernel's copy of the control word. Established.
  - libGLcore `__glCrmFlushAndConfirm`: writes 0 to `+0x21f8` then loops, with no limit, until status bit 28 is 1. `crm_pick` does the same before it writes `+0x21f0` when that write would clear bit 0. Established. The X module reads no status word.
  - Bits 27 and 26 are not read by shipped software; bit 25 is tested by `mte_spin`, which can never take effect (the test is compiled to a constant). Established. [reset.md](../../software/kernel/reset.md) has the details.
- Model-safe behaviour: bit 28 reads 1 whenever the model has no work in flight and the queue is empty, and reads 1 with level 0 at reset. A model that runs primitives to completion at the commit write and reports idle at once satisfies every poll above, but it must set bit 28 before libGLcore's unbounded loop and before `crmIdleWait`'s timeout (1 microsecond per step). Bits 27:25 should read as idle (1) when idle. Inferred for the bit meanings below 28, established for bit 28.
- `[binary]` The kernel regards a level of 65 or more as overflow (message `Cfifo Overflow! Current level at %d (ctl 0x%x)` printed with `level - 1`), so the field can read above 64 if the ring is overrun. What the ring contents are then is unknown.

## What a CPU sees when the buffer fills

- `[public]` Above the control word's stall level, the host interface stalls CPU writes to the engine for the stall cycle count, in 66 MHz cycles; above the interrupt level an interrupt is raised, which the handler either clears by polling the level or by enabling the empty interrupt (PDF 185 to 186). The specification gives no bit positions for these fields.
- `[binary]` The kernel's four threshold words build the control word as `count | stall << 7 | empty << 14 | full << 21` (`crimeError` shows the shifts in one place, `crimeInitHW` writes the same layout; 7-bit fields). First value `0x0fefff0a` (full 127, empty 63, stall 126, count 10): no stall or interrupt can occur below a level of 126. Then, by CPU module, full 20, empty 0, stall 19 (R10000 family and RM7000) or full 48, empty 24, stall 47 (R5000 class). Established. Reading full as the interrupt level and stall as the stall level, count as the stall cycle count (10 cycles of 66 MHz), fits the specification's three names; that mapping is inferred, as the specification gives no layout.
- `[binary]` Hence, on that mapping, the host interface stalls writes for 10 cycles of 66 MHz when the level is above 19 (or 47) and the full interrupt (input 26) asserts at 20 (or 48); `crimeFifoFullHandler` raises the full threshold to `level + 1` so the interrupt does not stay asserted, sleeps the writing thread, sets the empty threshold from `crmFifoWait`'s target when a waiter exists, and restores the full threshold in `crimeFifoEmptyHandler` (input 25). Established from the handlers' stores; the stall cycle semantics are the specification's.
- `[binary]` libGLcore and the X module never read the level. They write at full speed and rely on the stall; neither contains code that retries a store. Established ([opengl.md](../../software/opengl/opengl.md)). So the CPU-visible effect of fullness in a stock run is bus stall time and, above the interrupt level, scheduling delay. No bus error, dropped write or special read value appears in any shipped path.
- Model-safe behaviour for a model with no queue timing: never stall, never raise input 26, report level 0, and leave the interrupt inputs 25 to 27 deasserted. With an instantaneous model the kernel never waits. A model that does keep a queue must give a reader of the status word a level at or below 64 and may delay stores. If it raises input 26, `crimeFifoFullHandler` checks the interrupt bit and the level and counts the interrupt as spurious when the bit is clear.
- Unknown: the hardware's behaviour when the ring overruns (entries lost, stored over, or stores stalled indefinitely). Routes tried: the kernel's overflow message (names the condition, does not describe the data), libGLcore and X module (never reach it), the specification (silent). No shipped software depends on it.

## Facts for the register documentation

For whoever owns `registers.toml` and the generated pages (not changed here):

- `ib_discard` (offset `0x4008`): the register's description should read that shipped software writes 0 after table and register loads and after saving queued writes and that no shipped code relies on dropping writes; the hardware effect stays unknown/inferred (`start` follows the write pointer). The current text "the write discards the queued writes not yet committed" is contradicted by the call pattern above and should be changed to inferred-weak or removed. Name candidates are the owner's.
- `ib_reset` (`0x408`): add that the write is always followed by a 10 microsecond wait and a control-word write, that TLB survival is inferred, and that the writer sites are `crimeInitHW`, `crimeError`, `crime_earlyinit` and the diagnostics.
- `ib_ctl` (`0x400`): note that the register is read by the kernel's overflow message and, at two sites, by the PROM, which tests bit 0 only (clear: graphics record revision B, set: revision C) and never writes it. Write-only is the specification's classification, not what the software assumes; field mapping stays inferred.
- `status`: bit 28 `idle` established; level bits 24:18 established; kernel treats 65 or more as overflow; the idle-wait condition is idle and level 0.
- `ib_addr` and `ib_data`: both are read by the kernel; the address half with doubleword or word loads, the data half with word loads.

## Review (2026-11-24)

An independent re-read of this page against the 6.5.30 kernel objects and `ip32prom.image`.

- Confirmed: 18 stores of 32-bit zero to `+0x4008` in `crime.a` (`crime.o` 6, `crime_init.o` 4, `crime_tiles.o` 5, `crime_dma.o` 3) and none in `kernel.o`; `crimeValidateClip` stores it after ClipMode, the five screen masks and the two window words (`0x23e4`, in the delay slot of the branch that follows); `crmLoadCidTlb` stores it last. Stores of zero to `+0x408`: `crime.o` at `0x5204` and `0x5800`, `crime_init.o` at `0xbe4`, none in `kernel.o`.
- Confirmed: `crmIdleWait` (`crime.o` `0x2dbc`) polls until status bit 28 is set and bits 24:18 are 0, with `us_delay(1)` between polls; `crmSavePP` (`0x2ff8`) takes `wr_ptr` from bits 11:6 and `start` from bits 5:0; `crimeFifoFullHandler` loads `+0x400` at `0x344`.
- Confirmed: the specification's Table 7-1 lists the data RAM, the address RAM at `+0x200` and the write-only control word at `+0x400` with no register at `+0x408` or `+0x4008`; its 128-entry count conflicts with the 512-byte spacing.
- Grade: "established (the contradiction)" for the name `ib_discard` rests on the reasoning that the kernel's table loads are queued writes a discard would drop. That is an inference about the hardware's queueing, not an observation, and the page's own model-safe behaviour (accept the write, change nothing) is the sound reading. Treat the contradiction as inferred, strong.
- Fixed: the `+0x400` PROM bullet and the register-documentation note. The PROM does not test the bit against a board-record flag to "choose a function table"; it uses bit 0 to name the graphics record revision B or C and to pick a timing entry (resolved lead from the earlier pass).
- Not re-checked: `rd_ptr` bits 17:12 being unread by shipped software, the `mte_fifo_wait` and `crmFifoWait` thresholds, the control-word field layout, the `crimeError` delay-slot ordering and the interrupt-handler details.
