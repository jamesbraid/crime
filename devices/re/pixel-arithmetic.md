# Pixel arithmetic: depth, blending and texel filtering

The arithmetic of the depth stepper and test, the blender and the texel filter of the CRIME rendering engine: bit widths, rounding and the order of operations. Register offsets and field layouts are in [devices/re/CRIME_RE.h](CRIME_RE.h).

Labels: **established** (read from the cited source or code), **inferred** (reasoned, with the reasoning), **unknown**. Sources:

- [spec]: the CRIME 1.5 Specification, revision 0.3 (PDF page numbers).
- [hdr]: the register layout headers shipped with IRIX 6.5.5 as the CRIME stack header 22 and the CRIME stack header 21. They declare each pixel-pipe register as a bit-field structure; the field names are cited, the layout restated in our own words.
- [gl]: IRIX 6.5.30 N32 `libGLcore` (`usr/gfx/arch/IP32CRM32`), by unit under `software/opengl/asm/` and function. The software rasteriser units under `software/opengl/asm/soft/` are the generic OpenGL fallback; they show the formula the library computes when it draws without the engine, not the engine's arithmetic.
- [ide]: the IP32 stand-alone diagnostics, 6.5.30 `stand/ide.IP32` (binary).

## Depth

### Vertex position (the 13.6 field)

- Established ([gl] `crm_astri`, `crm_context`): the library adds a bias of 135168.0 (`0x21000`, that is 4096 plus 0x20000) to every window x and y in single precision, so each value lies in [131072, 262144) where one unit in the last place is 1/64. The bias is part of the viewport centre, so the add happens in the viewport transform itself. **Established (published):** the O2 technical report lists "6-bit subpixel positioning for OpenGL coordinates" and a 4K x 4K address space ([published-sources.md](../../references/documents/published-sources.md#1-o2-technical-report-version-10)), which fixes the 6 fraction bits; the report does not describe the bias.
- Established ([gl], no `ctc1` anywhere in the extracted `libGLcore`): the library never changes the FPU rounding mode, so the process default applies. IRIX starts processes in round-to-nearest-even (inferred from the absence of any other setting; not read from the kernel).
- So each vertex coordinate written to Vertex.GL is the window coordinate rounded to the nearest 1/64, ties to even (inferred, from the two facts above). The engine reads bits 18:0 of the stored word as an unsigned 13.6 value holding `coordinate + 4096` (inferred strongly; see the Vertex.GL note in `devices/re/CRIME_RE.h`).

### Window z and the Zs, dz/dx, dz/dy words

- Established ([gl] `soft/so_xform` `SetDepthRange`, `crm_context`): window z is `scale * z_ndc + centre`, with `scale = 0.5 * (far - near) * M` and `centre = 0.5 * (near + far) * M`; near and far are first clamped to [0, 1], the two products are formed in double precision and stored as single-precision floats, and the per-vertex multiply-add is then single precision (re-read from `SetDepthRange`), where `M` is the depth maximum `0x3fffffff` the CRIME context stores. Window z therefore spans 0 to 2^30 - 1.
- Established ([gl] `crm_astri` `__glCrmFlatZTriangle`, `__glCrmSmoothCIZTriangle`, `__glCrmSmoothRGBZTriangle`, `__glCrmSmoothRGBAZTriangle`): the set-up computes the plane slopes A and B in single precision from the three vertices ([spec] PDF 199, equations 7 to 9), evaluates the start value at the integer pixel corner `(Xs, Ys)` found by clearing the low six bits of the start vertex's 13.6 words, as `Zs = z + A * (Xs - x) + B * (Ys - y)` (two multiply-adds, in that order), multiplies Zs, A and B by 64.0 and converts each to a 64-bit integer by truncation toward zero (`trunc.l.s`). Zs goes to `+0x21c8`, dz/dx to `+0x21d0`, dz/dy to `+0x21d8`.
- Established ([spec] PDF 212-213): the engine steps depth with a 25.12 two's complement stepper, `z(Xs + m, Ys + n) = Zs + m * dz/dx + n * dz/dy` ([spec] PDF 198-200, equation 6). The fragment's 24-bit depth is the stepper value with its 12 fraction bits truncated, then clamped to [0, 2^24). The specification tells the host to add 0.5 to Zs to get rounded rather than truncated depths.
- Established ([gl], same four routines): the 6.5.30 driver does not add that half unit. Zs, dz/dx and dz/dy are stored straight from the truncating conversion. A model must truncate, not round, to match the depths IRIX produces.
- Units, by construction: window z times 64 is 2^36 at the top of the range, so the register value is the 24-bit depth-buffer value (window z / 64) with 12 fraction bits, which is exactly the specification's 25.12 (inferred, from the agreement of the two scales; the clear value below uses the same units).
- Precision (established arithmetic): window z is a single-precision float, which carries 24 significant bits. For depth-buffer values of 2^12 and above, the float has fewer than 12 fraction bits left, so the low fraction bits of Zs are zero; at the top of the range the float's resolution is one depth-buffer unit. The slopes are rounded to single precision before scaling.
- Stepper width and the upper bits (inferred): the driver writes full 64-bit words, but every value it can produce fits in 37 bits (sign plus 24 integer plus 12 fraction). Whether silicon keeps more than 37 bits is unknown: no shipped software or published source depends on it. Test that would settle it: write a stepper with bits above 36 set and read back through the first fragment's colour or depth; the document route is the stepper register tables, for the stated width of each stepper.
- Where the stepper samples (inferred): Zs is the plane's value at the integer corner below and to the left of the start vertex, and the stepper moves in whole-pixel steps from there, so the depth of pixel (x, y) is the plane evaluated at the integer point (x, y), not at x + 0.5, y + 0.5. The specification says pixels are sampled at their upper left corner ([spec] PDF 198), which fits sampling at the integer point. No source states whether the engine adds a half-pixel step before the first fragment; the driver supplies no half-slope term, which also suggests it does not.

### Clamping (established, [spec] PDF 212)

After truncation the integer part is clamped to [0, 2^24): negative results become 0 and results of 2^24 or more become 2^24 - 1. The specification states the range but not the mechanism; for colour it describes a test of the top two bits of a 9-bit result ([spec] PDF 200-201), and whether depth uses an equivalent top-bits test (which would wrap results more than 2^24 out of range) is unknown: no shipped software or published source depends on it, because the driver's planes stay inside the clip volume. Test that would settle it: step a depth value past 2^24 and below zero in a one-pixel span and read the depth buffer; a document route is the depth stepper text in the specification beside its colour clamp text (PDF 200-201).

### The depth buffer and the test

- Established ([gl] `crm_pixel`, see `software/opengl/pixel-transfer.md`): depth sits in bytes 2:0 of the 32-bit depth/stencil pixel and stencil in byte 3.
- Established ([spec] PDF 213, table 7-25): the test compares the fragment depth zs with the stored zd using the function in Depth.func bits 27:25 (NEVER, LESS, EQUAL, LEQUAL, GREATER, NOTEQUAL, GEQUAL, ALWAYS, codes 0 to 7). Both operands are 24-bit values in [0, 2^24) after clamping, so the comparison is an unsigned 24-bit compare (inferred, by construction).
- Established ([hdr] `CrmDepthMode`): Depth.func is laid out as 4 reserved bits (31:28), `func` (27:25), `enTagClear` (24) and `clear` (23:0). The driver sets bit 24 only when depth testing is on and the drawable has no depth buffer, the stencil-only case already recorded in `devices/re/CRIME_RE.h` ([gl] `crm_depth` `__glCrmPassDepthFunc`). The header's name says bit 24 enables a "tag clear"; what the engine does with it is unknown: no shipped software or published source depends on more than the driver's one use.
- Established ([gl] `__glCrmPassDepthFunc`): the clear value in bits 23:0 is `(int)(M * clear_depth) >> 6` in double precision with truncation, masked to 24 bits, so `glClearDepth(1.0)` gives `0xffffff`. It uses the same units as the Zs integer part.

## Stencil

The stencil state words are Stencil.mode (`0x21e0`) and Stencil.mask (`0x21e8`); their field layout is in `devices/re/registers.toml`.

- Established ([spec] PDF 189, figure 7-6): one 32-bit depth/stencil word holds stencil in bits 31:24 and depth in bits 23:0, the same byte layout as above.
- Established ([spec] PDF 212): the rendering diagram runs depth stepping, the depth test, the stencil test and then stencil and depth masking, in that order. The figure does not give the discard branches or which stencil operation applies when depth fails. Unknown: the chip's rule for each combination of stencil and depth outcomes, and whether a disabled depth test takes the depth-pass operation. No shipped software or published source settles this.
- Established ([spec] PDF 214, Table 7-26): the eight comparison names match the depth table, written as stored stencil `s` against reference `ref`, so LESS is `s < ref`. The section is marked TBD. The OpenGL 1.2.1 stencil test (`references/code/opengl-registry/specs/gl/glspec121.pdf`, PDF 156, section 4.1.4) compares the masked reference with the masked stored value, so API LESS is `(ref & mask) < (s & mask)`. The driver's comparison code follows the API order, not the table's (inferred). The two disagree on which operand is which, and the shipped driver settles the orientation as a software expectation (next bullets).
- Established (what the driver writes, [gl] `__glCrmPassStencilMode`, `0x0d96d250`, 500 bytes, N32): Stencil.mode is built from the context's stencil state as reference in bits 31:24, comparison mask in 23:16 (the low byte of the API mask), comparison code in bits 14:12 (bit 15 stays clear), stencil-fail operation in 11:8, depth-fail operation in 7:4 and pass operation in 3:0, and stored to the mode register of both register windows. The comparison code is the API function's enum minus the NEVER enum, passed through unchanged (the low three bits of the function word at context `+1664`), so codes 0 to 7 are NEVER, LESS, EQUAL, LEQUAL, GREATER, NOTEQUAL, GEQUAL and ALWAYS. The operation codes come from a fixed mapping of the API operation: KEEP 0, ZERO 1, REPLACE 2, INCR 3, DECR 4, INVERT 5, and any other enum falls to 0. Established for the driver; the chip's reading of them is the next two bullets.
- Inferred (software expectation, comparison order): the shipped driver expects code 1 (LESS) to pass when the masked reference is below the masked stored value, that is the API's operand order, so the specification's table entries read mirrored (unless its `s` names the reference). The evidence: the driver passes the API function straight through with no operand swap, and the library's own software stencil test, built in `__glValidateStencil` (`0x0da06640`) for the same context fields, takes LESS as `(ref & mask) < (stored & mask)`, LEQUAL as `<=`, GREATER as `>` and GEQUAL as `>=` (reference on the left), EQUAL and NOTEQUAL on the masked values, NEVER and ALWAYS constant. So the order for codes 1, 3, 4 and 6 is: LESS ref < stored, LEQUAL ref <= stored, GREATER ref > stored, GEQUAL ref >= stored, each on values masked by Stencil.mode's mask. That the engine masks both operands is the same expectation, and not independent of it: a different order would make hardware LESS disagree with software LESS in one program. Conflict with the specification's table text stays open as to labels; no routine reads the chip. Codes 8 to 15 and bit 15: no shipped software writes them, unknown.
- Established names ([spec] PDF 214, Table 7-27): zero, keep, replace by reference, increment, decrement and bitwise invert; the table lists them in that order without values, which is not the code order (the driver's KEEP is 0 and ZERO is 1; inferred from the driver, the chip's order is not published). Operation codes 6 to 15: no shipped software writes them and no source defines them, unknown (the driver's mapping falls back to 0, so a shipped library never reaches them).
- Inferred (software expectation, saturation): the driver expects INCR (code 3) and DECR (code 4) to saturate at the top step and at 0. The API requires it (OpenGL 1.2.1, PDF 156), the driver passes INCR and DECR straight to the engine with no wrap compensation, and the library's software operation table (`buildOpTable`, `0x0da064a0`) saturates both: INCR keeps the value at the maximum, DECR keeps 0, INVERT is the bitwise complement within the stencil width. The specification is silent and the chip's own rule is read from no source. The ClearStencil routine (`0x0d96d970`) and the polygon-stipple loader use code 2 (REPLACE) and code 0 only, so no shipped path leans on wrap.
- Inferred: the driver writes the stencil write mask as 0 or 0xff on its depth path. Bits 31:8 of Stencil.mask have no established meaning.
- Inferred (driver expectation): the driver's tagged clear. Read in `__glCrmPassDepthFunc` (`software/opengl/decomp/CRIME/crm_depth.c`, N32 `libGLcore.so`): when depth testing is enabled with the tag flag set, it sets depth-control bit 24 and writes Stencil.mode `0x5002` (NOTEQUAL; KEEP on stencil failure, KEEP on depth failure, REPLACE on pass), with Stencil.mask 0 or `0xff` by the context's depth-mask flag. The generation-update clear in the same file writes Stencil.mode `0x7002` (ALWAYS, KEEP, KEEP, REPLACE) and sets the depth function to ALWAYS (`0x0e000000`) with the clear depth in bits 23:0. Not re-read: that depth writes are on and colour off in the materializing clear, and where the driver turns bit 24 off. This use of bit 24 differs from the stencil-only reading above. What the chip does with bit 24 is unknown.

## Smooth colour

- Established ([spec] PDF 200-201): each of R, G, B and A is iterated by its own 21-bit two's complement stepper in 9.12 form. The register words are in `devices/re/registers.toml` under `shade_start`.
- Established ([spec] PDF 198-201): the colour plane has the same form as the depth plane, `c(Xs + m, Ys + n) = Cs + A*m + B*n`. Software supplies the starting value and the X and Y slopes. The manual does not say which sample the starting value belongs to, so the anchor is unknown here.
- Established ([spec] PDF 200-201): the manual describes adding 0.5 to a starting value as the software method for rounding instead of truncating. The driver adds no such half unit (see Blending).
- Established ([spec] PDF 200-201): colour-index shading uses the alpha stepper in place of the RGBA set. CI8 uses 8.12 and CI12 uses 12.8. Fractions are truncated, and the colour-index path performs no clamp.
- Established ([spec] PDF 201): the manual's clamp reads the top two bits of the truncated 9-bit integer. `[8:7] = 11` is underflow and gives 0; `[8:7] = 10` is overflow and gives 255. The manual assumes fragments inside the primitive do not overflow or underflow by more than 127, so their iterated integers stay between -127 and 382 (the bound read from the wording).
- Inferred: outside that assumption the manual gives no result. Read as a rule on the nine-bit field alone, the bits give 255 for field values 256 to 383 and 0 for 384 to 511, and the field's signed reading is -256 to -129 and -128 to -1 on those ranges. A clamp that sends every negative integer to 0 differs from this rule on -256 to -129, which the rule maps to 255. The manual's assumption is the only reason the two readings agree on the values a primitive produces.
- Unknown: what the stepper does when an iterated value leaves the 21-bit range between fragments, whether it wraps modulo 2^21 or saturates. The specification gives the width but no mechanism.

## Blending

- Read ([spec] PDF 208-210, equation 12): with DrawMode bit 10 set, each of R, G, B and A becomes `Cs * S op Cd * D`, where op is Blend.func bits 11:8 (ADD 0, MIN 1, MAX 2, SUBTRACT 3, REVERSE_SUBTRACT 4) and MIN and MAX ignore the factors. The factor codes (Blend.func bits 7:4 source, 3:0 destination) are the specification's tables; [hdr] the register layout header lists the same values, with SRC_ALPHA_SATURATE as source code 12. Blending applies to RGB(A) pixels only, after the antialiasing coverage stage and before dithering and the logic op ([spec] PDF 208-210).
- Established ([gl] `crm_attrib` `__glCrmPassBlendFunc`; see `devices/re/CRIME_RE.h`): on a drawable without alpha bits the driver rewrites DST_ALPHA to ONE and ONE_MINUS_DST_ALPHA and SRC_ALPHA_SATURATE to ZERO, so the engine never reads a missing destination alpha.
- The operands (established): the source colour reaching the blender is 8 bits per component. Flat colours are truncated from the float colour by the driver; smooth colours come from 9.12 steppers whose fraction is truncated and whose 9-bit integer is clamped to [0, 255] ([spec] PDF 200-201). The triangle set-up adds no half unit to the colour starts either ([gl] `crm_astri`: each start is stored as `trunc(c * 4096)` with no add after the conversion), so a smooth colour is truncated unless the vertex colour already carries a bias, which no routine read here adds. Destination components are the 8-bit fields of the stored pixel.
- The intended formula (established for the software path only): the generic software blender ([gl] `soft/so_blend`, `__glDoBlend_SA_MSA`, `__glDoBlendSourceSA`, `__glBlendSpan_SA_MSA`) works on single-precision floats: it scales alpha by the reciprocal of the alpha range (gc+30812), forms the factors in float, and computes `Cs * f + Cd * (1 - f)` (for the SRC_ALPHA, ONE_MINUS_SRC_ALPHA pair) as a multiply-add; conversion to the stored integer happens later in the span store. This is the OpenGL formula, not the engine's.
- Unknown: no shipped software or published source depends on it: how the engine multiplies an 8-bit component by an 8-bit factor (whether a factor of 255 means exactly 1.0, the width of the product and the rounding of the result), and whether ADD and SUBTRACT saturate or wrap. The only factor conversion the specification mentions for this engine is fog's: an 8-bit factor above 128 is incremented by one ([spec] PDF 206, whose sentence breaks off at "so that"). That 255 therefore becomes 256 and that the 1.8 product with 256 returns the colour unchanged is inferred from the 1.8 format, not stated. Whether the blender uses the same rule is unknown; it is the rule a model would most plausibly reuse (inferred, weakly, from the shared design). Saturating ADD and SUBTRACT to [0, 255] is what OpenGL requires and what the software path does through its clamped store; the specification is silent. Settling test: a capture of the engine blending known 8-bit source and destination values (factor 255 and 128, ADD and SUBTRACT overflow cases) read back from the frame buffer; the specification's missing sentence at PDF 206 would also settle the factor rule.

- Established absence ([spec] Table 7-20, PDF 208-209): the source factor table names SRC_ALPHA_SATURATE but gives no factor. The destination factor table (Table 7-21) has no such code. Equation 12 therefore has no defined saturate factor. The specification gives no clamp for the ADD and SUBTRACT results either.

### Dither

- Established ([spec] section 7.3.7.13, whose body is "TBD"; the DrawMode field table lists the enable): DrawMode has a dither enable bit. `devices/re/CRIME_RE.h` records it as bit 8 from the drivers, against the specification's bit 9 (the drivers are followed). Logic operations act on the colour after dithering ([spec] section 7.3.7.14), so dither comes before the logic op in the pipeline.
- Established (absence, searched 2026-11-10 over the pixel-state register list in `devices/re/CRIME_RE.h` and the register scans in `software/opengl/opengl.md`): no pixel-state register holds a dither matrix, offset or seed, and the driver library writes only the enable bit (`__glCrmEnableDither`). The matrix is therefore fixed in the engine.
- Established (software table, [gl] `__glDitherTable`, 16 bytes at `0x0da47a38` in the N32 `.data` and `0x0da4e930` in the o32 `libGLcore.so`, identical bytes): in row-major order `0 8 2 10 / 12 4 14 6 / 3 11 1 9 / 15 7 13 5`, a 4 by 4 ordered-dither matrix with entries 0 to 15. Every reader indexes it as `((y & 3) << 2) + (x & 3)` and takes one entry per pixel for all channels: `__glDitherRGBASpan` (`0x0da01bc0`), `__glDitherCISpan` (`0x0da017f0`), their stippled forms, the pixmap store routines and the memory-buffer stores `StoreSPBuffRGBA` and `StoreSPBuffRed` of the `crm_rgb` unit. The span routines scale the channel by 16, add the half, add the table entry, shift right by 4 and clamp from above only, so the offset is `t/16` of a destination step and never negative. The memory-buffer stores add `(2t+1)/32` to the scaled channel and truncate. All of these write surfaces the engine does not draw into.
- Inferred (software expectation about the engine): the driver assumes the engine's dither leaves a channel unchanged when it is an exact multiple of the destination step. `ClearRGBA` (`0x0d967980`, N32; the o32 notes describe the same test) takes the kernel's buffer-clear request (ioctl `0x5606`, which writes one undithered packed word) only when dither is off or every channel is on the grid, and otherwise draws a rectangle through the engine with the context's dither bit (DrawMode bit 8) copied in. In the 8-bit layout (3:3:2) the grid is: red and green with the low five bits clear, blue with the low six clear, and 255 also allowed (it packs to the top step). The 16-bit layout (5:5:5:1) and 32-bit layout make no such test, and the 16-bit one packs the channel truncated by 3 bits, so the driver is indifferent to dither there. That fits an engine that adds a non-negative offset below one step before truncating, which is the software's form. It does not fit one that rounds around the step or subtracts. It names no matrix. The driver supplies nothing else about the engine: no routine loads or reads a table for it, and the X module, kernel and `ide.IP32` never mention dither.
- Established (format widths, [gl] `ClearRGBA` layouts): a dither removes 5, 5 and 6 bits from red, green and blue in the 8-bit layout, 3 bits per colour in the 16-bit layout, and nothing in the 32-bit layout. Unknown: whether the engine dithers alpha or the one alpha bit of the 16-bit layout.
- Unknown: no shipped software or published source depends on it: the engine's matrix, whether the engine indexes it by window-relative or framebuffer-relative position, and what it does to a pixel off the grid. The software indexes the span's own x and y, inferred to be window-relative (not traced to every caller). A window origin that is not a multiple of 4 would tell the two apart, and the driver never tests for one. The software table is the candidate, so an emulator that uses it is making a choice, not following a finding. iris's note that its matrix comes from the library's software spans is accurate and says nothing about the engine. The technical report limits dithering to 3:3:2 and 5:5:5 targets ([published-sources.md](../../references/documents/published-sources.md)). Routes tried: the specification (section 7.3.7.13 is "TBD"), the register scans (no table register), the span, store, clear and pixmap routines of both builds, the X module, the kernel and `ide.IP32`.

Routes tried for the blend arithmetic: the specification (equation 12 and the factor tables only; its dithering section is "TBD"); [hdr] (field layout and codes, no arithmetic); [ide] (the 6.5.30 `ide.IP32` strings: the visual tests draw flat points, lines and rectangles and compare a CRC of the frame buffer; none enables blending, depth, fog or texture); [gl] hardware set-up (selects codes only) and software path (float OpenGL formula); Linux `gbefb`, NetBSD `crmfb`, MAME `crime.cpp` and GXemul the emulator-side device model source unit 2 (none models the pixel pipe's blender, depth or texture stages). Not read: the O2 libraries of IRIX 6.3; they cannot change the answer, because the blend is computed in the engine after the driver has selected codes. Published sources, searched 2026-10-29 ([published-sources.md](../../references/documents/published-sources.md)): the O2 technical report, the unified-memory and digital-media white papers, the graphics-implementations paper and the one patent on the chip give the order of operations (destination read in the colour pipeline, depth and stencil discard first) and the 8-bit operand width, and no product width, rounding or saturation rule; the dither is limited to the 3:3:2 and 5:5:5 formats, with no matrix.

## Logic ops

- Established ([spec] PDF 210-211, Table 7-23, section 7.3.7.14): when DrawMode's logic-op enable is set, a bitwise operation combines the source colour, after dithering, with the destination colour read from the frame buffer. The sixteen operations, with `s` the source and `d` the destination, are CLEAR `0`, AND `s&d`, AND_REVERSE `s&~d`, COPY `s`, AND_INVERTED `~s&d`, NOOP `d`, XOR `s^d`, OR `s|d`, NOR `~(s|d)`, EQUIV `~(s^d)`, INVERT `~d`, OR_REVERSE `s|~d`, COPY_INVERTED `~s`, OR_INVERTED `~s|d`, NAND `~(s&d)` and SET `1`.
- Established ([spec] section 7.3.1.17): the LogicOp register's field table is empty, so the numeric code for each operation is not given in the specification. `devices/re/CRIME_RE.h` takes the codes from the drivers.
- Logic ops apply to both colour-index and RGBA pixels ([spec] section 7.3.7.14).

## Fog

The register words and the stage's arithmetic are in [opengl.md](../../software/opengl/opengl.md#fog); this records what the library computes and writes, checked against the N32 `libGLcore.so`.

- Established ([gl] `RenderPointFog`, `0x0d95c8b0`): the start word is the vertex fog factor (a float, 1.0 unfogged) times 255.0 times 4096.0, truncated to an integer and stored through the start alias of `+0x2178` (`+0x2978`); the two slopes are zero for a point. The literals are the double 255.0 and the float 4096.0 in the routine's constant pool. So the word is a two's-complement value with the factor scaled to 0 to 255 in the integer part and 12 fraction bits: the specification's register map and the driver agree on this 9.12 reading, and its prose table calls the same words 1.20, which is the same bits scaled by 256/255 and which no software uses.
- Established ([gl] `__glCrmAntiAliasLineRGB`, `0x0d933200`; `__glCrmTexturedLine`, `0x0d94cf20`): for a line the start is the first end's factor times 255 times 4096, and the slope along the major axis is `(f1 - f0) * 255 * 4096` over the major-axis length, written to `+0x2180` for an x-major line or `+0x2188` for a y-major one, with the other slope zero.
- Established ([gl] `__glCrmRenderCheapFogLine`, `0x0d94bcb0`, store sites `0x0d94bd4c` and `0x0d94bd60`): untextured fogged lines are pre-blended per vertex on the CPU and the stage is parked at start `0x000ff000` (255 in the integer part) with slope 0 at both register windows. [`libglcore.md`](../../software/opengl/libglcore.md) gave `0xf000` for this constant until it was corrected from the instruction pair at `0x0d94bd38`.
- Inferred: with start 255 and slope 0 the stage's factor is 256 over 256, exactly the incoming colour; this rests on the specification's "increment above 128" rule (its sentence breaks off) and not on a read of the engine.
- Unknown: no shipped software or published source depends on it: the rounding of the product `f * (Cr - Fc)` and the stepper width beyond the 12 fraction bits (routes in opengl.md under "Fog").

## Antialiased lines

- Established ([gl] `__glCrmPickLineProcs`, branch at `0x0d951b8c`, as read in opengl.md): the library sets DrawMode bit 12 and the Primitive word `0x01040040` only for lines of width at most 1, in RGB, with no line stipple and no software-fog or software-texture fallback. Anything wider, stippled, colour-index or falling back is drawn by the software line and point routines. The library leaves blending to the application; it never turns blend on for an antialiased line.
- Established (composed state in shipped use, [gl] `__glCrmAntiAliasLineRGB` and `__glCrmTexturedLine`): the hardware antialiased line is issued together with flat or smooth shading, fog steppers and depth steppers (`__glCrmAntiAliasLineRGB`), and together with texturing (`__glCrmTexturedLine`, which tests GL_LINE_SMOOTH, bit `0x200` of the enable word at context `+1792`, at `0x0d94cf64`, skips the antialias block when it is clear at `0x0d94d394`, and otherwise stores the slope-and-position word and the two end-coverage values as one 64-bit store to `+0x2190` at `0x0d94d4a8`). So the engine is expected to compose line coverage with the texture, fog, depth, shade and blend stages. It is not asked to compose it with line stipple, width other than the fixed pair, colour index, or the polygon and point paths (points and polygons are covered in software).
- Established ([gl] the same routines): the words the engine receives are the 2.14 slope and 2.14 ideal minor coordinate in `+0x2190` and the two endpoint coverages in `+0x2194`, computed as in opengl.md; the library supplies the inputs and never a coverage table.
- Inferred: the engine's coverage is multiplied into the alpha after fog and before the alpha test (specification, section 7.3.7.10), so a visible effect needs blend; the pipeline order is the specification's, the shipped software never contradicts it.
- Unknown: no shipped software or published source depends on it: the contents of the two coverage ROMs, the endpoint filter, the rounding of `alpha * coverage`, and what the engine does with antialiasing on while a stage the library never combines with it is also on (stipple, wide lines, colour-index pixels, DrawMode bit 13).

## Alpha test

- Established ([spec] PDF 207, section 7.3.7.11): the alpha test compares the fragment's alpha after antialiasing coverage has been applied. It applies only to RGB(A) pixels, is enabled by DrawMode bit 11, and discards the fragment when the comparison fails. The driver's glAlphaFunc reference is scaled to the 8-bit field as described in [opengl.md](../../software/opengl/opengl.md).
- Established ([spec] PDF 180, AlphaTest register; PDF 207, table 7-19): the reference is bits 7:0, an 8-bit value, and the function is bits 11:8. Bits 31:12 are reserved. The function codes are NEVER 0 (false), LESS 1 (`alpha < ref`), EQUAL 2 (`alpha == ref`), LEQUAL 3 (`alpha <= ref`), GREATER 4 (`alpha > ref`), NOTEQUAL 5 (`alpha != ref`), GEQUAL 6 (`alpha >= ref`) and ALWAYS 7 (true).
- Unknown: function codes 8 to 15 have no entry in the specification's table, so their behaviour is not known. No shipped software or published source sets one.
- Unknown: the order of the alpha test against the depth and stencil tests. The specification gives the coverage-then-alpha-test order and says nothing about depth or stencil relative to it.

## Texel filtering

### Coordinates reaching the filter

- Established ([spec] PDF 203-204, figure 7-15 and table 7-17): the engine steps s/w, t/w and 1/w as 36.12, 36.12 and 18.12 values, divides, maps (s, t) to (u, v), computes a level of detail, looks texels up and filters them.
- Established ([gl] `crm_astextri` `__glCrmFillTriangle`): the driver scales s/w and t/w by 2^43 (or 2^39 for a coordinate flagged in `+0x2134`) and 1/w by 2^29, truncates each start and slope toward zero, and then adds 2048 to each of the three starts (`+0x2120` sq, `+0x2128` tq, `+0x2130` q) but not to the slopes. 2048 is one half in the steppers' 12-bit fraction, which is inferred to be the same half-unit adjustment the specification recommends for colour and depth starts ([spec] PDF 201, 212); the specification does not mention it for the texture steppers. If the engine truncates their fractions, the added half unit rounds to nearest. The driver does not do so for depth or colour (above).
- Established ([hdr] `CrmTextureReg`): the 32-bit word at `+0x2134` is named `stShift`, which agrees with the reading in `software/opengl/opengl.md` that its two bits select a four-bit shift of the s and t steppers.
- By inference ([gl] scales, as in `devices/re/CRIME_RE.h`): after the divide a texture coordinate of 1.0 is 2^14. Texture.format shifts it right by `10 - log2(size)` (the `uShift` and `vShift` fields, so named in [hdr]), leaving a texel coordinate with 4 fraction bits, and the index masks keep `log2(size) + 4` bits, which implements GL_REPEAT by masking. The maximum size is therefore 1024 texels per side, which [hdr] the register layout header states as a maximum level of detail of 10 and [spec] PDF 202 as 1k by 1k.
- Established ([gl] `__glCrmFillTriangle`): the driver applies no half-texel offset to s or t for linear filtering; no constant 0.5 enters the set-up.

### Level of detail

- Established ([spec] PDF 204, figure 7-16): the engine takes the four differences of u and v between a fragment and its right and upper neighbours and computes `rho = max(du/dx, dv/dx, du/dy, dv/dy)` and `LOD = log2(rho)` (the magnitudes are implied, inferred). This is not the generic software formula: [gl] `soft/so_texture` `__glComputePolygonRho` sums squared u and v derivatives per axis before taking the larger, the OpenGL length form.
- Unknown: no shipped software or published source depends on it: the precision of the LOD (integer only or with a fraction), how the fraction weights the two levels in the MIPMAP_LINEAR modes, and the magnification-to-minification switch point. The specification's sections on texel look-up and on minification and magnification filtering are "TBD" ([spec] PDF 205). Settling test: a capture of the engine texturing a mipmapped checker with a known scale ramp, read back to see where the level switches and how the fraction blends; no document or binary read is expected to settle it.

### Filter weights

- Read ([spec] PDF 202, [hdr] the register layout header): the filter codes are NEAREST 0, LINEAR 1, NEAREST_MIPMAP_NEAREST 2, LINEAR_MIPMAP_NEAREST 3, NEAREST_MIPMAP_LINEAR 4, LINEAR_MIPMAP_LINEAR 5 (Texture.mode bits 9:7), with magnification NEAREST or LINEAR in bit 6.
- Inferred (from the 4 fraction bits above): a bilinear weight has at most 4 bits, sixteen steps per texel.
- The intended formula (established for the software path only): [gl] `soft/so_texture` `__glLinearFilter2` computes `u = s * width - 0.5` (after clamping s for the clamp modes), `i0 = floor(u)`, `i1 = i0 + 1`, `a = frac(u)`, likewise `b` for v, fetches the four texels as floats and returns `(1-a)(1-b) t00 + a(1-b) t10 + (1-a) b t01 + a b t11` in single precision, with no quantisation of the weights. `__glLMLFilter` filters both levels and blends them as `(1 - f) * level_a + f * level_b`, where f is the fraction of the level of detail (`__glFrac`), again in float.
- Unknown: no shipped software or published source depends on it: whether the engine applies the half-texel offset itself (the driver does not, so a conformant engine must), how the 4-bit weights are formed (truncation of the coordinate fraction is the plain reading), the order and width of the products and the rounding of the filtered 8-bit components, and the arithmetic of texture application (MODULATE, DECAL, BLEND, REPLACE; [spec] PDF 205 names them only). Settling test for the filter arithmetic: draw a bilinear-filtered rectangle from a one-row texture whose two texels are `0x00` and `0xff`, stepping the s coordinate by one sixteenth of a texel per pixel across the span, and read the pixels back. Where the ramp starts shows whether the engine applies the half-texel offset, the number of distinct intermediate values shows the weight width (sixteen if the weights have 4 bits), and the values at exact eighths show whether the product truncates or rounds. This is a hardware test and needs the hardware proposal the project requires; no document or binary read is expected to settle it.

Routes tried for the filter: as for blending, plus the generic software texture unit and the format and mode headers. A model that truncates the 4-bit fractions, weights the four texels with products of those fractions and truncates the result is consistent with every established field, but it is a choice, not a finding. Published sources, searched 2026-10-29 ([published-sources.md](../../references/documents/published-sources.md)): the technical report says the divide is floating point and the level of detail per pixel, and no source gives a weight width; a predecessor patent gives a level fraction linear in the maximum derivative (`(LOD >> fine) - 1.0`), a candidate for the unknown level-of-detail fraction, inferred and unconfirmed for this chip.

## Review (2026-11-24): stencil, dither, fog and antialiased lines

An independent re-read against the N32 `libGLcore.so` (sha256 `3806c89f...`) and the o32 build (sha256 `a1c6d7e2...`), both from the 6.5.30 disk.

- Confirmed (stencil word): `__glCrmPassStencilMode` (`0x0d96d250`, 500 bytes) builds reference `lh` of context `+0x686` in 31:24, the low byte of `+0x688` in 23:16, `(word at +0x680) & 7` in 14:12 (bit 15 cleared), operations from `+0x68c`, `+0x690`, `+0x694` in 11:8, 7:4, 3:0, and stores to `+0x21e0` of both register windows. Operation map: 0 gives 1, `0x1e00` gives 0, `0x1e01` gives 2, `0x1e02` gives 3, `0x1e03` gives 4, `0x150a` gives 5, anything else 0. Codes 6 to 15 are never written.
- Confirmed (comparison order): the software stencil test built by `__glValidateStencil` (`0x0da06640`, jump table at `0x0da4517c`) computes LESS as `ref < stored`, LEQUAL as `not (stored < ref)`, GREATER as `stored < ref` read as `ref > stored`, GEQUAL as `not (ref < stored)`, with both operands masked and EQUAL and NOTEQUAL on the masked pair. The driver passes the enum's low three bits straight through. The page's orientation (API operand order) is right as a software expectation and graded inferred for the engine.
- Confirmed (saturation): `buildOpTable` (`0x0da064a0`) computes INCR as `i + 1` unless `i` is the maximum (kept), DECR as `i - 1` unless `i` is 0 (kept at 0), INVERT as `~i`, KEEP as `i`, ZERO as 0, REPLACE as the reference, and merges the result under the write mask. `ClearStencil` (`0x0d96d970`) ORs `0x7000 | 0x200 | 0x20 | 0x2` into the mode word: comparison ALWAYS and REPLACE for all three operations. The specification's stencil section is "TBD" and Table 7-27 lists the six names in zero, keep, replace, increment, decrement, invert order (checked in the PDF text).
- Confirmed (dither table): `__glDitherTable` is 16 bytes of `0 8 2 10 / 12 4 14 6 / 3 11 1 9 / 15 7 13 5` at `0x0da47a38` (N32) and `0x0da4e930` (o32), the same bytes. `__glDitherRGBASpan` (`0x0da01bc0`) indexes it with `((y & 3) << 2) + (x & 3)`, adds the entry to the scaled channel, shifts right by 4 and clamps above only. `ClearRGBA` (`0x0d967980`) takes the buffer-clear ioctl `0x5606` only when dither is off or the channels lie on the destination grid: in the 8-bit layout red and green with the low five bits clear and blue with the low six clear (255 also allowed, the grid test covers `0x1f`, `0x1f` and `0x3f`); the 16-bit path (`0x0d967e7c`) has no dither test. The page's grade (a software table, not engine evidence) is right.
- Confirmed (fog): `RenderPointFog` (`0x0d95c8b0`, no dynamic symbol) multiplies the vertex fog factor by the double `255.0` (`0x406fe00000000000` at `0x0da4b678`) and the float `4096.0` (`0x45800000` at `0x0da4b784`) and stores the truncated word at `+0x2978`; `__glCrmRenderCheapFogLine` (`0x0d94bcb0`) forms the start `0x000ff000` with `lui 0xf` and `ori 0xf000` at `0x0d94bd38`, stores it to `+0x2178` at both windows and stores a value to `+0x2180`. The specification's register map labels `Fog.Fs`, `Fog.dfdx` and `Fog.dfdy` 9.12 two's complement; its prose table calls them 1.20 and the two disagree, as the page says. The correction to `libglcore.md` (0xff000, not 0xf000) is right.
- Confirmed (antialiased lines): `__glCrmAntiAliasLineRGB` (`0x0d933200`) stores the fog start to `+0x2178` and the slope to `+0x2180` or `+0x2188` by the major axis, and stores 64-bit words to the start alias `+0x2990` of the antialias register (not `+0x2190` itself; the page's `+0x2190` names the register); `__glCrmTexturedLine` (`0x0d94cf20`) stores a 64-bit word to `+0x2190` at `0x0d94d4a8`.
- Not re-checked: the exact scale constant in the dither span (the constant loaded from the pool before the add), `RenderPointFog`'s zero slopes, the o32 notes, the polygon-stipple loader's stencil codes, `__glCrmPickLineProcs`'s width and stipple conditions, and the claim that the library never turns blend on for an antialiased line.
