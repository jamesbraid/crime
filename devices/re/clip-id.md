# Clip-ID plane and the ClipMode clip-ID test

What the rendering engine's clip-ID translation table points at, how the plane is laid out, who fills and clears it, and what ClipMode bits 11 and 10 select. Registers are in [registers.md](registers.md) (`tlb_cid`, `clipmode`); the transfer-engine side is in [../mte/mte.md](../mte/mte.md).

Labels: **established** (read in full from the cited code or table), **inferred** (reasoned, reasoning given), **unknown** (routes tried listed). Provenance tags: `[binary]` a shipped IRIX 6.5.30 O2 object read here (kernel `crime.a` members, the X module `crm.so`, `libGLcore.so`, `ip32prom.image`, `gfxinit`); `[public]` the CRIME 1.5 specification (PDF page numbers as in the other pages); `[hdr]` a name shipped in a published header (names only). No `[source]` fact is used.

## The translation table

- `[public]` The table is `TLB.cid[4]`, 64-bit registers, global, at `+0x6e0` of the specification's TLB map, which is `+0x16e0` of the engine base (Table 7-2, PDF 164). Entries name 64 KiB tiles. The specification gives no entry layout.
- `[binary]` The only code in the shipped kernel that stores to `+0x16e0` is `crmLoadCidTlb` (`crime.a(crime_tiles.o)`, `.text` +0x2464). It takes an entry count from word `+4` of the plane record and a list of 16-bit entries through the pointer at `+8`, packs four entries into a doubleword (entry `j` in slot `j & 3`, slot 0 in the top 16 bits), stores doublewords at `0x16e0 + 8 * (j / 4)` and always writes all four doublewords, entries past the count as zero, then writes 0 to `+0x4008` ([interface-buffer.md](interface-buffer.md)). Established, whole body read.
- `[binary]` The entries are the kernel tile list unchanged. `crmAllocTiles` stores each tile as the physical address shifted right by four from the allocator's page-frame word, which is a 16-bit tile number with no flag bit ([memory.md](memory.md)). The frame-buffer loader and the texture loader set bit 15; this one does not. Established. Whether bit 15 must be set for the engine to accept the tile is inferred from the other tables only; see Unknown below.
- `[binary]` Callers: only `crmInitialize` in `crime.a(crime.o)` reaches `crmLoadCidTlb`, directly after `crimeInitHW` and the two `crmLoadTlbABC` calls, with the plane record at `+0x2d0` of the graphics state. No context-switch, drawable-validation or resize path reloads it. Established: no other call site in `crime.a`, and no other store to registers `0x16e0` to `0x16f8` in the kernel text (the offset `0x16f8` also appears twice, as address arithmetic in the linear-TLB clear loops of `crimeInitHW` and `crmValidateDrawable`, where the pointer has already advanced by 16 from `0x1700`). The table is therefore a per-screen setting made once at screen start-up.
- `[binary]` No store to `+0x16e0` exists in `crm.so`, `gfxinit` or `libGLcore.so`, and the only occurrences of that immediate in `ip32prom.image` are not stores to the engine. Established as absences of the instruction pattern; `ide.IP32` is not on the held disk and was read in an earlier pass ([reset.md](../../software/kernel/reset.md)), which found no cid store.

## Allocation and what the tiles hold

- `[binary]` `crmAllocCid` (`crime_tiles.o`, `.text` +0x11ac) takes the plane record, the screen width and the screen height, and returns 0 on success. With any width other than 1280 it asks the tile allocator for `(height + 127) / 128` tiles in class 0 (the chunk type word stored at `+12` of the record is 8), leaving that count at `+4` and the tile list at `+8`. Established, whole body read. The old reading of this routine, "a fixed set of 16 when its first argument is `0x500`", was wrong on two counts: the argument is the width (1280 pixels), and no tiles are requested then.
- `[binary]` With width 1280, `crmAllocCid` requests zero tiles (type word 16), zeroes the 32-byte table, and fills entry `i` from the overlay buffer's tile list (the kernel's `crmOverlayBuffer`, not `crmFrameBuffer`; the relocations at `.text` `0x1264` and `0x126c` name it): the last tile of overlay tile row `i`, taken as list index `(i + 1) * tiles_per_row - 1` for `i` from 0 to `(height + 127) / 128 - 1`, where `tiles_per_row` is the byte at `+0x18` of the overlay record. Established, whole body read. The plane then shares physical tiles with the overlay buffer.
- `[binary]` The overlay buffer is allocated at one byte per pixel (`crmAllocOverlayBuffer`, `crime_tiles.o` `.text` `0x1128`, takes `(width + 511) / 512` tiles per row and `(height + 127) / 128` rows, and stores the per-row count at `+0x18`), whatever the depth of the main frame buffer. A 1280-wide overlay is three tiles per row of 512 bytes, so the last tile holds overlay pixels 1024 to 1279 in byte columns `0x000` to `0x0ff` and leaves `0x100` to `0x1ff` unused, which is exactly map 1. Inferred: that is why the 1280 case needs no tiles of its own, and drawing map 0 would overwrite overlay pixels 1024 to 1279, which is consistent with the shipped server using map 1 only. The main frame buffer is not aliased, so there is no collision at 16 or 32 bits (the first draft of this page said there was, reading the object as the frame buffer).
- `[public]` A 64 KiB tile is 128 by 128 pixels at 32 bits, 256 by 128 at 16 bits, or 512 by 128 at 8 bits (PDF 186). The transfer engine addresses a tile-mapped buffer by byte column in bits 31:16 and row in bits 15:0 of the destination word, and selects the plane with buffer code 6, "tiled buffer - clipID TLB" (specification, transfer-engine mode table; [../mte/mte.md](../mte/mte.md)). So the plane is addressed as a byte image, 512 columns by up to 2048 rows. Established (specification), with the one-tile-wide shape inferred from the allocation count: one tile per 128 rows and a table that holds no more than 16.
- `[binary]` Every transfer-engine access to the plane in `crm.so` uses byte columns `0x000` to `0x1ff` and rows up to the screen height (below). Established. A plane row therefore covers 256 byte columns per map, 2048 pixels; a screen wider than 2048 cannot be clipped by a plane. Inferred from the column count.

## Bit layout

- `[binary]` `crmDrawCID` (`crm.so` `0x516500`) fills the plane for a list of boxes (x1, y1, x2, y2 as four halfwords, x2 and y2 exclusive). Per box it divides x by 8 for the byte column and keeps `x mod 8`. The partial columns at the left and right edges come from two eight-entry-plus-one tables in `crm.so` read-only data. Both tables were read from the shipped file (6.5.30, `crm.so` 1,861,396 bytes) at pool offset `+8128` and `+8168` from the base the routine loads:
  - left edge, indexed by `8 - (x1 mod 8)`: `0x00`, `0x01`, `0x03`, `0x07`, `0x0f`, `0x1f`, `0x3f`, `0x7f`, `0xff` (each replicated into all four bytes of the word);
  - right edge, indexed by `x2 mod 8`: `0x00`, `0x80`, `0xc0`, `0xe0`, `0xf0`, `0xf8`, `0xfc`, `0xfe`, `0xff` (replicated likewise).
  Established (values read, indexing read from the instructions). They set the low `n` bits for the `n` covered pixels at a left edge and the high `n` bits for the `n` covered pixels at a right edge, which means pixel `x mod 8 = 0` is bit 7 and pixel 7 is bit 0, most significant bit leftmost. Established as the software's convention. That the engine's test uses the same bit for the same pixel is inferred: the plane is only ever written by the software above and has no other reader in shipped code.
- `[binary]` The routine writes a partial column by loading the mask word into the transfer engine's foreground value `+0x3018` with the byte mask `+0x3008` all ones, so a partial column replaces its whole byte. Boxes of one region that share a byte column (gap under 8 pixels) can therefore clear each other's edge bits; shipped code does nothing to prevent it. Established from the stores, inferred that the loss is real (it depends on the transfer engine replacing, not merging, bytes, which [../mte/mte.md](../mte/mte.md) covers).
- `[binary]` Set mode writes all ones across whole columns (`+0x3018` = `0xffffffff`), clear mode writes 0 over the same boxes, both with mode word `+0x3000` = `0x18` (clear, 8-bit depth, destination buffer 6), byte mask all ones and destination step 1. When the routine's map argument is 1 every box is shifted right by 256 byte columns, which puts it in map 1; the other non-zero value used is 2, which leaves map 0. Established.

## Reading the plane

- `[public]` ClipMode bit 11 is `enCid` ("enable clip ID testing"). Bit 10 is `cidMapSel`, whose description in the specification repeats the bit 11 text, so the specification does not say what the select does (Table 7-6, PDF 173).
- `[binary]` The shipped software uses the two bits exactly as follows (all established as stores): bit 11 alone (`0x800`) while the plane is drawn in map 0; bits 11 and 10 (`0xc00`) while it is drawn in map 1. The X module's `crmSetSmask` (`0x58a930`) writes `0x800` or `0xc00` according to the small-data word `use_cid` (2 gives `0x800` with `crmDrawCID` called with 2; 1 gives `0xc00` with it called with 1), and the kernel's `crimeValidateClip` writes `0x821` or `0xc21` (below). So bit 10 set means map 1, which is the half at byte columns `0x100` to `0x1ff`. Established for the software's pairing, inferred for the hardware: that the engine tests map 1 when bit 10 is set follows from the plane being drawn at +256 columns under the same bit.
- Inferred: with bit 11 set the engine draws a pixel only if the plane bit for that pixel is 1, because `crmDrawCID` sets bits over the visible area and the clear path writes 0 for the rest. No shipped software exercises a plane that is set outside the visible area, so the inverse sense is not excluded by a counter-example, only by the construction.
- Inferred: the test uses the pixel's final frame-buffer position, after the window offset is added. `crmDrawCID` writes the region boxes to the plane unchanged, and those are screen-space boxes, while drawing into the same windows uses window offsets (`+0x2058`); a plane built in screen space only matches if the lookup is in screen space. No shipped sequence shows whether the lookup position includes the window offset, so this rests on the construction only.
- `[binary]` The kernel's use is narrower: `crimeValidateClip` (`crime.a(crime.o)`, `.text` +0x21b0) chooses the ClipMode from the rectangle count in the clip description. One to five rectangles load that many screen masks and give `0x21 << ...` as before, with no plane test. Count zero loads screen mask 0 with the window's bounding box and gives `0x21`, or `0x821` when the description's word at `+0x24` is non-zero, plus `0x400` (`0xc21`) when the word at `+0x20` equals 1. Counts above five, and negative counts, give `0x21` and load no mask. Established, the ClipMode selection read in full. So a plane-tested draw is also limited by the bounding-box mask, and the plane takes over exactly the windows too complex for five rectangles. Who writes the description's `+0x20` and `+0x24` is not shown by the kernel (`crimeSetNullClip` sets them to -1 and 0): the clip request comes from the user-space resource manager through ioctl `0x55ff`, and the X module's own request builder was not followed word by word, so which shipped path ever sets `+0x24` is unknown. libGLcore never writes ClipMode (no store with offset 8208 in any CRIME unit of its disassembly).

## Who fills and clears it

- `[binary]` `crmInit` (`crm.so` `0x48a250`) reads `CRM_USECID` with `getenv` (the string is at pool offset `+2680`), converts it with `atoi`, stores 2 when the value is exactly 2 and 1 for any other value, including 0, into `use_cid` at `gp - 26728` (the store sits in the delay slot of the call that prints `Using CID in X rendering, cid = %d`, at `0x48a3c0`), and leaves it at its start-up value, zero, when the variable is absent. Established, instructions read. With `use_cid` zero, `crmSetSmask` and the line, segment and point routines take their screen-mask-only paths and never call `crmDrawCID`. So in a stock session the plane is never drawn and ClipMode bit 11 is never set by the X server.
- `[binary]` The clear is `crmInitHW..HB` (`0x58a2b0`), called from `crmInit`. After it clears the colour buffer through the pixel pipeline it clears the plane through the transfer engine: mode `+0x3000` = `0x18`, byte mask all ones, step 1, foreground 0, destination start `0x01000000` (byte column `0x100`, row 0), destination end `0x01ff0000 | (height - 1)`, flush `+0x3078`. The start is a branch on the routine's third argument: when it equals 2 the start is column `0x100`; any other value starts at column 0, which would clear both maps. The only caller passes the word `crmRRMPriv + 4`, initialised to 2 and never stored (read earlier, [opengl.md](../../software/opengl/opengl.md)). So the shipped server clears map 1 and leaves map 0 alone. Established. The height is the halfword at `+10` of the screen record.
- Unknown: whether the tile allocator hands out zeroed tiles, which would make map 0 start clear. Routes tried: `crmAllocTiles` (it calls `tile_alloc` with a flag word and does not touch the memory), the kernel allocation helpers in `kernel.o` named around it. Every shipped path that sets plane bits first clears the plane, or uses map 1, so no software depends on map 0 being clear at start-up. A model may start both maps zero.
- `[binary]` The remaining plane writes are per window: `crmDrawCID`, `crmValidateClip` and the stereo helper `nfbStereoDrawCID..II` clear and set boxes through the same transfer-engine words. Not expanded here; [xmodule.md](../../software/xsgi/xmodule.md) lists them.

## Unknown

- Whether the engine requires bit 15 of a clip-ID table entry to be set. No shipped code sets it, so either the engine ignores the bit for this table or the bit does not exist for it. Routes tried: all stores to the table in the kernel (one), the diagnostics read earlier ([memory.md](memory.md)), the specification (gives no entry layout), NetBSD (does not use the table). A model should accept entries without the bit and use the low 14 bits as the tile number, as for the other tables. Unknown beyond that: no shipped software or published source depends on it.
- What a plane-tested draw does when the plane's table has no entry for the pixel's row (a row beyond the allocated tiles, or a zero entry). Routes tried as above; the screen height is never beyond the allocated count in shipped code.
- The exact engine behaviour on a clip-ID test at a position outside the table (rows 2048 and up). No shipped caller can reach it.
- The environment variable's value 2 selects map 0 and its tests have not been run: the pairing of value 2 with `0x800` is read from `crmSetSmask` only.

## Facts for the register documentation

For whoever owns `registers.toml` and the generated pages (not changed here):

- `tlb_cid`: entry format as above, graded established for the entry (tile number, no flag bit, four per doubleword, slot 0 in bits 63:48), the zero fill past the count, and the single loader. The kernel stores all four doublewords every time.
- `clipmode` bit 11 `clip_id_test`: pass if the plane bit is 1 (inferred). Bit 10 `clip_id_map`: 0 selects byte columns `0x000` to `0x0ff` of the plane, 1 selects `0x100` to `0x1ff` (established for the software pairing, inferred for the hardware). The specification's duplicated description for bit 10 should be recorded as a specification defect.
- The MTE destination code 6 plane geometry: 512 byte columns by up to 2048 rows, one bit per pixel, most significant bit leftmost.
- `set_startptr` is written at the end of the loader ([interface-buffer.md](interface-buffer.md)).

## Review (2026-11-24)

An independent re-read of this page against the 6.5.30 `crime.a` members, `crm.so` and the CRIME 1.5 specification.

- Confirmed: `crmLoadCidTlb` (`crime_tiles.o` `0x2464`) packs entry `j` into slot `j & 3` of a doubleword (slot 0 in the top 16 bits), always runs `j` from 0 to 15 with entries past the count left zero, stores doublewords at `0x16e0 + 8 * (j / 4)` and then stores 0 to `+0x4008`; the loop reads the count from `+4` and the list from `+8` of the plane record.
- Confirmed: `crimeValidateClip` (`crime.o` `0x21b0`) ClipMode words: `0x21 << i` accumulated over the rectangle count (so `0x21`, `0x63`, `0xe7`, `0x1ef`, `0x3ff`), `0x821` for count zero with the word at `+0x24` non-zero, `0xc21` when the word at `+0x20` is also 1, and plain `0x21` for counts above five or negative.
- Confirmed: `crmSetSmask` takes `use_cid` from `gp - 0x6868`: zero takes the screen-mask path, 1 stores `0xc00`, anything else `0x800`. `crmInit` reads `CRM_USECID` with `getenv`, converts it with `atoi` and stores 2 when the value is 2 and 1 otherwise, absent leaves zero. `crmInitHW..HB` clears map 1 only when its third argument is 2 (start `0x01000000`, end `0x01ff0000 | (height - 1)`, mode `0x18`, byte mask all ones). The two edge tables are present once in `crm.so` with the printed values.
- Confirmed: `crmAllocCid` branches on the width argument equal to `0x500`.
- Wrong, fixed: the tile list `crmAllocCid` copies at width 1280 is the overlay buffer's, not the frame buffer's, so the plane aliases the overlay (one byte per pixel at every depth), not the frame buffer, and the 16- and 32-bit collision concern did not exist. The conclusion that the aliased half is map 1 stands for the overlay.
- Not re-checked: that `crmDrawCID` is called with 2 for `0x800` and 1 for `0xc00` (the argument is set in a code path not followed), the `crmValidateClip` and `nfbStereoDrawCID..II` per-window writers, and the entry layout facts that rest on `crmAllocTiles`.
