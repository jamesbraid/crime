# The IRIX 6.5.30 kernel on an O2 with an R5000: Config, clock, caches, TLB and CPU-keyed CRIME programming

The IP32 kernel decides what to do from the CP0 PRId implementation byte, reads a handful of Config fields once at
boot, measures the CPU clock against the CRIME timer and writes only one Config field on an R5000 (SE, in several
places). EC and EP are never read by the 6.5.30 IP32boot objects. This page records that, with the R5000-only workarounds, the
cache and TLB set-up, and the one place the kernel programs CRIME from the CPU number. It reads the 6.5.30 IP32 kernel
objects `usr/cpu/sysgen/IP32boot/kernel.o` and the members of `os.a` (`startup.o`, `machdep.o`, `pda.o`, `tlbmgr.o` and
the others named below), disassembled with relocations. The 6.5.22 and earlier kernels were not read. The firmware half
is `platforms/ip32/prom-r5000.md` in the chips workspace. No hardware, no guest run.

Labels: **established** (the routine read in full), **inferred**, **unknown**. Addresses are offsets in the named
object's `.text` (`kernel.o` unless a member is named). PRId implementation numbers: `0x23` R5000, `0x28` RM52xx,
`0x27` RM7000, `0x09`/`0x0e`/`0x0f` R10000 family, `0x20`..`0x22` R4600 family.

## Reading the CPU

- **PRId is read through `get_cpu_irr`** (`0x13610`) at roughly 130 call sites: `kernel.o`, 22 members of `os.a`
  and 17 other objects (`io`, `kmem`, `ds`, `efs`, `xfs`, `crime`, `a3_dd` and others). Apart from the sites below, each
  one is the same split: implementation below `0x23` (R10000 family, R4x00) against `0x23` and above, in memory-
  addressing, page-allocation, DMA and cache-flush code. None refuses an R5000. The shipped `coproc_find` (`machdep.o`,
  `0x9c`) reads it first, keeps the raw word, and rewrites implementation `0x28` to `0x23` in the copy it keeps (a
  `0x28` part is treated as an R5000). `fp_find` (`0x11628`) does the same to FCR0, which it reads through
  `get_fpc_irr` (`0x1362c`: save Status, clear it, set only CU1, `cfc1 $0`, restore). **Established.**
- FCR0 is recorded, tested for nonzero (nonzero means an FPU is present and `fp_init` runs) and reported in the
  hardware inventory; only its implementation byte is otherwise tested. A model may return any nonzero FPU revision
  (the observed `0x2310` works). **Established.**
- The PRId word `0x2321` (revision 2.1) takes the normal path everywhere found. The only revision-sensitive tests are
  below.

## R5000-only workarounds and their gates

- **FP convert workaround.** `coproc_find` clears a kernel flag `R5000_cvt_war` unless the PRId major revision
  (bits 7:4) is 1. The boot arguments `r5000_cvt_war` (any R5000) and `rm5271_badvaddr_war` (`0x28` only) can set the
  flags explicitly. The illegal-instruction fast path `handle_ii` (`0x1fdf0`) runs only when
  `PRId & 0xfff0 == 0x2310`, that is revision 1.x. It looks at the instruction at EPC (or EPC+4 in a delay slot), tests
  for a coprocessor-1 word with format field 0x17, ft = 0 and function `0x20` or `0x21` (convert), requires Status.CU1,
  and reads a floating register chosen by fs. With PRId `0x2321` the handler goes straight to the general trap path.
  The match is **established**; that it works around an R5000 revision 1 convert erratum is **inferred** from the
  flag name.
- **TLB refill.** For `0x23`, `0x27` and `0x28` the boot code (`initmasterpda`, `pda.o` `0x4a8`; also
  `_hook_exceptions`, `0x14f60`) installs one table: `utlbmiss_r5000` (`0x15784`) and its extended variant instead of the
  generic handlers. The `0x28` difference is that `_r5000_badvaddr_war` is set. `0x20` and `0x21` get the R4600
  handlers. The R5000 refill handler loads the pair, executes `tlbp`, and writes the entry with `tlbwr`
  only if the probe missed (Index bit 31 set); if the probe hit it jumps to the general exception vector `0x80000180`
  instead. **Established.** (**Inferred** reason: avoiding a write of a duplicate entry. A model must therefore make
  `tlbp` and Index.P correct inside the refill handler.)
- **Page colouring.** `mlreset` (`0x8738`) sets `cachecolormask` to 7 and then recomputes it from the primary D-cache
  way size: for an R5000 with a 32 KiB two-way D-cache the way is 16 KiB, so mask 3. For implementation below `0x23` it
  then zeroes the mask. A flag `is_r4600_flag` is set for `0x20`, `0x21`, `0x23`, `0x27` and `0x28` (jump table at
  `.rodata+0xa78` in the function at `0x83c8`) and `vce_avoidance` is 1 for the two-way parts. **Established.**
- **K0.** Only the R10000 family (`0x09`, `0x0e`, `0x0f`) gets a Config write there (K0 := 5). Every other implementation
  keeps the K0 the PROM left, 3. **Established** (same table).

## Finding the CPU clock

`_cpuclkper100ticks` (`0x140f8`) is the calibrator; `findcpufreq_raw` (`0x13b78`) converts; `cpu_mhz_rating`
(`0x13e44`) rates; `timestamp_init` (`0x89d8`) stores the result as the timer rate. **Established.**

1. Preload the loop into the I-cache with Fill I (CACHE `0x14`), then four times: write Count := 0 and the CRIME timer
   (`0xb4000038`, doubleword) := 0, poll the CRIME timer's low word until it reaches 23 496 (`0x5bc8`), read Count.
2. Average both, then Count rate = Count average × (66 666 500 ÷ CRIME tick average). 66 666 500 is the CRIME timer rate
   the kernel assumes.
3. Round to the nearest of 39 nominal rates (66.58 MHz to 250.565 MHz). On PRId `0x23` three snaps follow: a result
   rounded to 87.55 or 87.64 MHz becomes 90.0 MHz, 97.953 MHz becomes 100.227 MHz and 150.345 MHz becomes 150.339 MHz.
   A measured rate more than about 4 MHz above the table end is kept unrounded.
4. `cpu_mhz_rating` doubles the rounded Count rate (add 0.5 MHz, divide by 1e6) and snaps to a nominal CPU rating, so
   the kernel assumes Count at half the pipeline clock for every CPU. `timestamp_init` takes the Count rate itself
   as the timer frequency.

A model with Count at exactly 100 000 000 Hz and the CRIME timer at exactly 66 666 500 Hz rounds to 100.227 MHz (the
nearest table value on the R5000 path), and the PRId `0x23` rating comes out as a 200 MHz CPU. Config is not consulted,
so EC does not affect any of this. **Inferred** for the final rating (a hand trace of the comparison chain, not
executed).

The clock tick uses the Compare interrupt (IP7). `r4kcount_intr_r4000` (`0xcee8`) takes a two-interval path for
implementations from `0x23` up (`t0interval`, `t1interval` over one Compare register) and, below `0x23`, first asks the
performance-counter code whether the interrupt was its overflow. `clr_r4kcount_intr` (`0x14cc`) clears IP7 by writing
Compare. **Established.**

## Cache and TLB set-up on an R5000

`config_cache` (`0x737c`) is called first thing in `mlsetup` (`startup.o`); `size_2nd_cache` (`0x77f4`) follows.
**Established.**

- Primary sizes: for `0x23`, `0x27`, `0x28` I size = `0x1000 << Config[11:9]`, D size = `0x1000 << Config[8:6]`. Every
  other implementation, the R10000 family included, reads Config[31:29] and Config[28:26] instead. These are the
  only Config bits the kernel reads for the primaries, so EC and EP bits are not read on the R5000 path, and the
  R10000's fields are not confused with them.
- Secondary: `size_2nd_cache` returns 0 when Config bit 17 (SC) is set, otherwise `0x80000 << Config[21:20]` (SS). The
  raw Config word is also kept at boot (`r4000_config`) and the cache-error handlers test SC in that copy. Line
  length is fixed: `scache_linemask` is 0x1f for the R5000 route and 0x3f otherwise.
- The kernel itself turns the R5000 secondary cache on: `_r4600sc_enable_scache` (`0x5c3c`) sets Config.SE (bit 12), after
  switching to the uncached alias, with Status cleared if ERL was clear. Unless the boot argument `triton_invall`
  is set it then invalidates the whole secondary cache with a Page Invalidate S loop (CACHE `0x17`, stride 4 KiB over the
  cache size). With that argument it does one Index Writeback Invalidate S (CACHE `0x03`) at index 0. **Established.**
  That the single operation invalidates the whole cache on the R5000 is **inferred** from the name and the code
  shape.
- `config_cache`'s other Config write, at `0x752c` (sets bit 3 after clearing it), is on the RM7000 branch only and never
  runs on an R5000. **Established.**
- SE is also cleared and set again at run time: `_r4600sc_disable_scache` (`0x5b9c`, clears bit 12) is called by
  `prom_autoboot` (before returning to the PROM), and enable/disable pairs bracket `ecc_handler` and
  `print_buserr_rev0`. **Established.**
- Cache operations present in the flush routines (`__dcache_inval`, `__dcache_wb`, `__dcache_wb_inval`, `__icache_inval`,
  `__cache_wb_inval`): Index Invalidate I (`0x00`), Index Writeback Invalidate D (`0x01`), Index Writeback Invalidate S
  (`0x03`), Hit Invalidate I/D/S (`0x10`, `0x11`, `0x13`), Fill I (`0x14`), Hit Writeback Invalidate D (`0x15`), Page Invalidate S (`0x17`; the R5000
  encoding, which the enable routine above also uses), Hit Writeback D (`0x19`) and, in `__dcache_wb`, `0x1b`. The
  R4600-family helpers `_r4600sc_inval_cache` and `_r4600sc_index_inval` also use `0x03`, `0x0b` (Index Store Tag S)
  and `0x17`. CACHE `0x16` and `0x02` appear in `_r4600sc_enable_scache` only on the RM7000 path. The routines choose among them by kernel flags (`scache_present`, set counts); which
  subset an R5000 with a 1 MiB secondary executes was not traced. **Inferred** for the subset. No cache-error or
  Create Dirty Exclusive operation was found on this path.
- TLB: `mlsetup` sets `ntlbentries` = 48 and `nrandomentries` = 38 for `0x23` and `0x28`, and 64 and 54 below `0x23`.
  For `0x27` it picks 48 and 38 when the secondary cache is below 2 MiB. `start` (`kernel.o` `0x1a10`) writes Wired :=
  10, PageMask := 0, Context high bits and zeroes Cause, EntryHi and Status; it clears WatchLo and WatchHi only for CPUs
  that are not `0x20`, `0x21`, `0x23`, `0x27`, `0x28`. **Established.**
- Low memory: below `0x23` a low-memory zone ends at page frame `0x800` (8 MiB) and a separate "extended K0" test
  (`is_extk0_pfn`) is live; from `0x23` up the zone size is 0 and `is_extk0_pfn` always answers no. **Established**
  as a branch; purpose **inferred**. No object read refuses or limits an R5000 by RAM size.

## CPU-keyed CRIME and MACE programming

Only one site writes CRIME from the CPU number. `mlreset` (`0x8738`), in this order, **established**:

1. Read CONTROL (`0xb4000008`), store 0 to `+0x48` and to `+0x250`.
2. `get_crimerev`: when the revision code is 0 (oldest CRIME), write `0x3ff` to `+0x50`.
3. Read PRId, take the implementation byte (arithmetic shift by 8). If it is below `0x23`, write CONTROL = saved value
   with bits 13:12 and bit 9 cleared (mask `~0x3200`). If it is `0x23` or above (R5000, RM52xx, RM7000), write CONTROL =
   saved value with bit 9 cleared and bits 13:12 set.
4. Write 0 to INTMASK (`+0x18`) and to `+0x10`, then flush the bus.

For an R5000 the value is therefore the boot-time CONTROL with bit 9 cleared and `0x3000` set. The branch is on the
implementation byte alone (not on a revision), so a model's PRId implementation field decides it. `mlreset` then clears the
MACE PCI error flags and writes the PCI control register with `0xfe008dff` or `0xfe0085ff` by a prefetch flag: neither
depends on the CPU.

No other kernel code programs CRIME, MACE or PCI from the CPU type. The only other CRIME-related CPU-keyed item is the
graphics driver's interface-buffer thresholds for CPU modules below `0x23` or equal to `0x27` (full level 20, empty
level 0) against 48 and 24 otherwise ([reset.md](reset.md), `crimeInitHW`), which gives an R5000 48 and 24.
**Established.**

## Config fields the kernel writes on an R5000

| Writer | Address | Field and value | When | Grade |
|---|---|---|---|---|
| `_r4600sc_enable_scache` | `0x5ccc`..`0x5d00` | SE (bit 12) := 1 | `config_cache` when SC is clear; `ecc_handler` and `print_buserr_rev0` re-enable | established |
| `_r4600sc_disable_scache` | `0x5bf8`..`0x5c04` | SE := 0 | `prom_autoboot`, `ecc_handler`, `print_buserr_rev0` | established |
| the R10000 branch of the function at `0x83c8` | `0x840c`..`0x8420` | K0 := 5 | R10000 family only, not an R5000 | established |

Nothing else writes Config on an R5000. K0 stays 3 from the PROM; EC, EP, SC, SS, SB, EB, EM, EW, bit 15 and the
reserved bits are never written. (Bit numbers are the VR5000 manual's: SB 23:22, EB 13, EM 14, EW 19:18; bit 3 is
reserved and the `0x752c` write is RM7000-only.) The kernel reads SC (boot code and the cache-error handler), SS, IC and
DC, and, for the line-size helper used by the ECC routines, IB (bit 5), DB (bit 4) and SB.

**SB and the cache-error path.** The helper at `0xfa74`, inside `r_phys_word_erl` (`0xfa6c`), reads Config live and
returns `16 << SB` as the secondary line size; the caller at `0xfaf4` selects it when SC is clear. It is reachable on
PRId `0x23`: `_hook_exceptions` installs `_ecc_errorvec` at `0xa0000100` for every CPU, and the chain `ecc_exception`,
`ecc_panic`, `ecc_same_cache_block` (`0xfb60`) ends in that helper. It runs only on a Cache Error exception. **Established**
for the chain's shape; the model needs SB = 1 (32-byte lines) so this path computes the right block size.

## Unknown

- Whether R5000 reset-time EC and EP are set by the module's mode stream, and what a factory module carries: no software
  in the 6.5.30 IP32boot objects or PROM 4.8 and 4.18 reads them. Routes tried: every Config read in those objects and
  images. **Unknown: no shipped software depends on it.**
- Which CACHE operations an R5000 with a 1 MiB secondary actually reaches in the flush routines (selection by flags not
  traced).
- 6.5.22 and earlier kernels were not read.
